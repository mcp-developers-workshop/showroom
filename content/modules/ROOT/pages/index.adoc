= MCP in Practice
A Hands-on Workshop for developers, architects, and platform engineers

Welcome to the *MCP in Practice* hands-on workshop.

Model Context Protocol (MCP) provides a standard way for AI applications to discover and use tools and data from external systems. MCP servers are to AI applications what APIs are to traditional applications: a standard way to access enterprise capabilities without needing to know how those capabilities are implemented.

That sounds simple. In an enterprise environment, it is not.

== The Globex journey

Let's explore the journey through the lens of Globex, a fictitious retail company. 

Like most ecommerce retail platform, customers login and place orders. Usually an identity provider authenticates the user, and the web app calls the backend systems, passing information such as the userid or email address on behalf of the user.

This is the flow such a traditional application:

[source,text][source,text]
----
Customer → Web Application → REST API → Backend Systems [Catalogue, Orders, etc.]
----

image::intro/globex-intro.png[Globex AI Journey]

Globex now wants to provide online customer support to handle customer queries faster and provide a better customer experience. To do so, Globex introduces Glo, an AI-powered customer support agent that can help customers with their order queries and product complaints.

Connecting an AI application to enterprise systems such as databases, REST APIs, SaaS platforms, means deciding what capabilities to expose, what data those capabilities should return, who is allowed to use them, and how to understand what happened when something goes wrong.

With MCP, the architecture looks like this:

[source,text]
----
Customer → AI Application → MCP/MCP Server → Backend Systems [Catalogue, Orders, etc.]
----

image::intro/globex-intro-ai.png[Globex AI Journey]

The AI application can discover available tools and determine when to use them. MCP standardizes how the enterprise capabilities are exposed and invoked, but it does not decide what an enterprise should expose, who should be allowed to use it, or what data should be returned.

These areas remain engineering and governance decisions, and they are the focus of this workshop.

=== The Challenges

As Glo moves from a simple prototype toward a production application, Globex encounters a few practical challenges:

* *What should Glo be allowed to access?* +
Expose the right capabilities without giving the agent unrestricted access to backend systems.
* *What data reaches the model?* +
Return only what the agent needs rather than passing entire backend responses into the model context.
* *Who is making the request?* +
Give agents and services a verifiable identity and enforce authorization.
* *What happened when something goes wrong?* +
Trace requests across the agent, MCP servers, model, and backend services.
* *How do you manage MCP at scale?* +
Apply tool access, credentials, and policies centrally rather than configuring every agent independently.

This workshop takes you through the Globex journey, with each module addressing one of these challenges.

You will start by building an MCP server and exposing purposeful, intentional tools. You will then connect those tools to an AI application, add identity and authorization, make the interactions observable, and finally introduce a gateway to control MCP access at scale.
