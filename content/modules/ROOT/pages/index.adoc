= MCP in Practice
A Hands-on Workshop for developers, architects, and platform engineers

Welcome to the *MCP in Practice* hands-on workshop.

Model Context Protocol (MCP) provides a standard way for AI applications to discover and use tools and data from external systems. MCPs are to AI apps what APIs are to traditional applications: a standard way for AI apps/agents to access enterprise capabilities without needing to know how those capabilities are implemented.

That sounds simple. In an enterprise environment, it is not.

Connecting an AI application to enterprise systems such as database, REST API, SaaS platform, or internal service means deciding what capabilities to expose, what data those capabilities return, who is allowed to use them, and how to understand what happened when something goes wrong.

This is the flow in a traditional application:

[source,text][source,text]
----
Customer → Web Application → REST API → Backend Systems
----

Now introduce an AI application using MCP, and it looks like this:

[source,text]
----
Customer → AI Application → MCP → MCP Server → Backend Systems
----

The AI application can discover available tools and determine when to use them. MCP standardizes how those capabilities are exposed and invoked, but it does not decide what an enterprise should expose, who should be allowed to use it, or what data should be returned.

Those remain engineering and governance decisions decisions, and they are the focus of this workshop.

* What capabilities should an MCP server expose?
* How much data should a tool return to the model?
* Who is making the request, and what are they authorized to do?
* How do you trace a request across the AI application, MCP server, and backend?
* How do you control MCP access as the number of servers, clients, and tools grows?

This workshop explores those questions through the story of *Globex, a fictitious retail company* introducing an AI-powered customer support agent called *Glo*.

You will start by building an MCP server and exposing purposeful tools. You will then connect those tools to an AI application, add identity and authorization, make the interactions observable, and finally introduce a gateway to control MCP access at scale.

The goal is not simply to build an MCP server. It is to understand what changes when MCP moves from a local developer experiment to an enterprise integration point.

== The Globex journey

Globex starts with a simple requirement: give *Glo, the agent* access to its existing enterprise systems to helps its customers.

As the application evolves, so do the engineering requirements 

* *What should the agent be allowed to access?* +
Expose the right capabilities without giving the agent unrestricted access to backend systems.
* *What data reaches the model?* +
Return only what the agent needs rather than passing entire backend responses into the model context.
* *Who is making the request?* +
Give agents and services a verifiable identity and enforce authorization.
* *What happened when something goes wrong?* +
Trace requests across the agent, MCP servers, model, and backend services.
* *How do you manage MCP at scale?* +
Apply tool access, credentials, and policies centrally rather than configuring every agent independently.

This workshop walks you through this journey through a series of modules, each building on the previous one.
