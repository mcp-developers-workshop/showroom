= Summary

:numbered:
:icons: font
:source-highlighter: highlight.js

You put the Globex complaints MCP server behind a watsonx Orchestrate agent without writing any code:

* Cloned a workspace of three YAML files, one folder per artefact kind, and pointed two of them at your cluster.
* Created a connection holding the Keycloak realm and the client credentials grant, then set the client ID and secret as flags so they live in Orchestrate rather than in the repository.
* Registered the complaints MCP server as a toolkit backed by that connection, and listed the tools to prove Orchestrate had really reached the server rather than just accepted the file.
* Defined a native agent naming the four tools it may call, with its own instructions, welcome message and starter prompts.
* Asked it for a prioritised list of product improvements and watched the request turn into a schema inspection, a query over the most recent complaints, and a ranked answer.

The split between the connection and the toolkit is the part worth keeping. The toolkit says where the server is and what it offers; the connection says how to authenticate to it. Credentials can be rotated, or swapped for a different environment's, without touching the tool definitions -- and the agent never sees them at all, because Orchestrate attaches the token on the way out.

Note too that the reach of the agent is limited in two separate places. The toolkit took `tools: "*"` and imported everything the server advertises, but the agent lists its four tools explicitly and cannot call anything outside that list. Narrowing at the toolkit controls what exists in the workspace; narrowing at the agent controls what one agent can do with it.

The same MCP server you built and secured in earlier modules is being consumed here by something that is not a Quarkus application and shares no code with one. That is the protocol doing its job.

What this does not solve is scale. You configured one connection and one tool list by hand; at twenty servers and thirty agents, every consumer carries its own copy of the credentials and its own copy of the rules about who may call what, and they drift. A gateway is where that same separation lives when it has to be enforced once rather than repeated -- one place holding the credentials, one place defining which consumer sees which tools.

== Where this goes next

The improvements the agent produced are displayed in the chat and go no further. In a real product organisation they would become tracked work.

[NOTE]
====
This workshop can be extended by registering an external MCP server for an issue tracker -- Jira, for example -- as a second toolkit in the same workspace, and giving the agent its issue-creation tool alongside the four complaints tools.

The agent would then do in one turn what currently takes a person copying the output: read the complaints from one MCP server and open the resulting improvements as issues in another. Nothing about the complaints server would change. The connection and toolkit pattern you used here is the same one the second server would need, which is the point -- adding a capability is adding two YAML files, not writing an integration.
====
