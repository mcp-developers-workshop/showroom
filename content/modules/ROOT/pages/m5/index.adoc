== Overview & Objectives
This final module addresses enterprise tool sprawl and centralized governance by introducing an MCP Gateway (ContextForge). You will configure the gateway to aggregate multiple downstream MCP servers (GitLab, Complaints DB), create isolated Virtual Servers, enforce granular tool filtering rules, and connect personal productivity agents securely.

=== Learning Objectives
* Understand the challenges of enterprise tool sprawl and decentralized agent access.
* Configure ContextForge MCP Gateway as a centralized reverse proxy and governance layer.
* Register downstream enterprise MCP servers (GitLab MCP Server, Complaints DB MCP Server).
* Implement strict Tool Filtering (e.g., exposing only `create_issue` and `get_issue` from GitLab).
* Set up Virtual Servers with dedicated authentication for personal productivity agents (Bob CLI / watsonx Orchestrate).

== Architecture & Components
* *MCP Gateway:* ContextForge Gateway
* *Downstream MCP Servers:* GitLab MCP Server, Complaints DB MCP Server
* *Client Agents:* Personal Productivity Agents (Bob CLI, watsonx Orchestrate)
* *Governance Features:* Virtual Servers, Tool Filtering Policies, Centralized AuthN/AuthZ

== Prerequisites
* OpenShift environment with ContextForge Gateway deployed
* Access to enterprise GitLab repository and Complaints DB MCP Server

== Lab Agenda
1. Clone the Orchestrate workspace and point it at your cluster
2. Create a connection holding the Keycloak realm and OAuth client credentials
3. Register the complaints MCP server as a toolkit backed by that connection
4. Define a native agent over the toolkit's tools and deploy it
5. Chat with the agent and confirm it reaches the MCP server

== Expected Outcomes
A centralized, governed MCP Gateway architecture enforcing tool access policies and providing single-pane-of-glass management for enterprise AI integrations.
