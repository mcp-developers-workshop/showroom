= Module 5: Centralized Governance
:numbered:
:icons: font
:source-highlighter: highlight.js

== Overview & Objectives

Establishing a centralized MCP Gateway to configure virtual servers, manage authentication, and enforce strict tool filtering rules.

One MCP server consumed by one agent needs no governance. Twenty servers and thirty agents do. Every agent needs credentials for every server it touches, and the rules about which agent may call which tool get copied into each one, where they drift apart.

This module is about where those controls belong: a centralized gateway that holds the credentials, presents each consumer a virtual server carrying only the tools it is allowed to see, and enforces the filtering rules in one place.

The lab works through that separation against the Globex complaints MCP server. You keep its credentials in a connection, distinct from the tool definitions that use them, and you narrow what is reachable in two independent places -- what is imported from the server, and what a single agent is permitted to call.

[NOTE]
====
The lab uses watsonx Orchestrate, but the platform is incidental. What you define is a connection, a toolkit, and an agent with an explicit tool list -- the same separation a gateway applies centrally, with the MCP server behind it unchanged either way.
====

=== Learning Objectives

* Understand why decentralized agent access to MCP servers becomes a governance problem at scale.
* Register a remote MCP server as a toolkit, without writing code.
* Keep the OAuth credentials in a connection, separate from the tool definitions that use them, so they can be rotated or swapped per environment.
* Enforce tool filtering at two independent levels: what is imported from the server, and what one agent may call.
* Ask the agent for a product improvement report and confirm from the tool calls that it came from the MCP server.

== Architecture & Components

* *Governance model:* credentials in a connection, tools in a toolkit, an explicit per-agent tool list
* *MCP server:* the Globex complaints MCP server, on its read-only endpoint
* *Client platform:* watsonx Orchestrate, driven by the `orchestrate` CLI
* *Authentication:* Keycloak `internal` realm, client credentials grant, held in the connection
* *Data:* the `complaints` table in the Globex store database

== Prerequisites

* A watsonx Orchestrate instance and an API key for it
* The complaints MCP server from the earlier modules deployed and reachable from outside the cluster

== Lab Agenda

1. Clone the workspace and point it at your cluster
2. Create a connection holding the Keycloak realm and OAuth client credentials
3. Register the complaints MCP server as a toolkit backed by that connection
4. Define an agent over a narrowed subset of the toolkit's tools and deploy it
5. Chat with the agent and ask it for a product improvement report

== Expected Outcomes

A deployed agent that reaches the complaints MCP server over authenticated HTTP, holds no credentials of its own, and can call only the tools it was explicitly granted -- answering a request for product improvements with a prioritised list grounded in the complaint data, with its tool calls visible in the chat.
