= Module 5 Lab: Connections, MCP Toolkits, and Agent Deployment
:toc: left
:toclevels: 3
:numbered:
:icons: font
:source-highlighter: highlight.js

This lab covers creating a *Connection*, configuring *OAuth credentials*, registering a remote *MCP Toolkit* backed by that connection, and importing a *Native Agent* with UI prompt customization in IBM watsonx Orchestrate.

Each artefact is a YAML file imported with the `orchestrate` CLI, and the order matters. The toolkit's `app_id` refers to the connection, so the connection must exist and hold valid credentials first. The agent's `tools` refer to the toolkit's tools, so the toolkit must be imported before the agent.

[NOTE]
====
The commands below use the watsonx Orchestrate ADK CLI (`orchestrate`). It must be installed and pointed at an active environment before you start.
====

Your project workspace needs the following resource folders:

----

== Define and Import the Connection

A connection stores the target endpoint and authentication specification without hardcoding secrets.

.connections/globex-complaints-connection.yaml
[source,yaml,role="copypaste",subs="attributes+"]
----
spec_version: v1
kind: connection
app_id: globex-complaints-connection
environments:
  draft:
    security_scheme: oauth2
    auth_type: oauth2_client_creds
    type: team
    server_url: https://sso.{openshift_subdomain}/realms/internal
    token_url: https://sso.{openshift_subdomain}/realms/internal/protocol/openid-connect/token
----

[cols="1,2", options="header"]
|===
| Field | Meaning

| `app_id`
| The name the toolkit and CLI commands use to refer to this connection.

| `environments`
| Per-environment settings. `draft` is the development environment; a `live` environment can hold different credentials for the same `app_id`.

| `security_scheme` / `auth_type`
| OAuth 2.0 using the client credentials grant, so the agent authenticates as itself rather than as a user.

| `type: team`
| Credentials are shared by everyone in the team, rather than stored per user.

| `server_url` / `token_url`
| The Keycloak realm protecting the complaints MCP server, and the endpoint the client credentials are exchanged at for a token.
|===

Import it:

[source,bash,role=execute]
----
orchestrate connections import -f connections/globex-complaints-connection.yaml
----

Importing only registers the specification. The connection is not usable until you configure it and set credentials in the next section.

== Configure the Connection and Set Credentials

Configure the connection flow for the `draft` environment and supply the OAuth client credentials.

Configure the auth flow:

[source,bash,role=execute]
----
orchestrate connections configure \
  -a globex-complaints-connection \
  --kind oauth_auth_client_credentials_flow \
  --type team \
  --env draft
----

This tells Orchestrate which OAuth flow the connection uses. It has to match the `auth_type` in the YAML.

Set the OAuth credentials, replacing `<YOUR_CLIENT_ID>` and `<YOUR_CLIENT_SECRET>` with your own values:

[source,bash,role=execute,subs="attributes"]
----
orchestrate connections set-credentials \
  -a globex-complaints-connection \
  --env draft \
  --client-id "<YOUR_CLIENT_ID>" \
  --client-secret "<YOUR_CLIENT_SECRET>" \
  --token-url "https://sso.{openshift_subdomain}/realms/internal/protocol/openid-connect/token"
----

[IMPORTANT]
====
The client ID and secret come from the `internal` Keycloak realm, from the client registered for the complaints MCP server. TBC -- confirm the client name and where attendees obtain the secret.
====

The secret is stored by Orchestrate against the connection. It does not go in the YAML file, which is why the YAML is safe to commit.

== Register the MCP Toolkit

The MCP toolkit connects to the remote MCP server using the configured connection.

.toolkits/globex-complaints.yaml
[source,yaml,role="copypaste",subs="attributes+"]
----
spec_version: v1
kind: mcp
name: globex-complaints
description: This MCP server helps in getting details about complaints that were raised and also provide a nice summary for product improvement perspective.
transport: streamable_http
url: https://globex-complaints.{openshift_subdomain}/read/mcp
app_id:
  - globex-complaints-connection
tools:
  - "*"
----

[cols="1,2", options="header"]
|===
| Field | Meaning

| `kind: mcp`
| Registers a remote MCP server rather than a local Python or OpenAPI tool.

| `transport: streamable_http`
| Matches the transport the MCP server was built with in Module 1.

| `url`
| The MCP endpoint on the complaints server. The `/read/mcp` path exposes the read-only tools.

| `app_id`
| References the connection created above. Orchestrate attaches a token from that connection to every call.

| `tools: "*"`
| Imports every tool the server advertises. Naming tools individually here is one way to limit what an agent can reach; the gateway covered in this module is the other.
|===

Import it:

[source,bash,role=execute]
----
orchestrate toolkits import -f toolkits/globex-complaints.yaml
----

=== Verify the imported tools

The import succeeds even if the server is unreachable, so list the tools to confirm Orchestrate actually connected and read the tool definitions:

[source,bash,role=execute]
----
orchestrate tools list
----

You should see:

* `globex-complaints:get_last_1000_complaints`
* `globex-complaints:read_query`
* `globex-complaints:list_tables`
* `globex-complaints:describe_tables`

Tools are namespaced by toolkit name, which is why each entry is prefixed with `globex-complaints:`.

_TBC: screenshot -- `orchestrate tools list` output with the four globex-complaints tools._

[NOTE]
====
If no tools are listed, the toolkit imported but Orchestrate could not reach the MCP server or could not authenticate. Check the `url` and re-run the `set-credentials` step.
====

== Define and Import the Native Agent

Create the agent specification with tool mappings, instructions, starter prompts, and a custom welcome message.

.agents/complaints_analyser.yaml
[source,yaml,role="copypaste"]
----
spec_version: v1
kind: native
name: complaints_analyser
display_name: Complaints Analyser
description: An agent that retrieves and analyses customer complaints, providing detailed summaries and actionable insights for product improvement.
llm: groq/openai/gpt-oss-120b
style: react_core
tools:
  - globex-complaints:get_last_1000_complaints
  - globex-complaints:read_query
  - globex-complaints:list_tables
  - globex-complaints:describe_tables
starter_prompts:
  is_default_prompts: false
  prompts:
    - id: prompt_1
      title: Top complaint types
      subtitle: ''
      prompt: "What are the top 5 most common complaint types and how many times does each appear?"
      state: active
    - id: prompt_2
      title: Complaints by severity
      subtitle: ''
      prompt: "Show me a breakdown of complaints by severity. How many are Critical or High?"
      state: active
    - id: prompt_3
      title: Products by complaint volume
      subtitle: ''
      prompt: "Which products have the most complaints? Rank them by complaint volume."
      state: active
    - id: prompt_4
      title: Unresolved complaint themes
      subtitle: ''
      prompt: "What are the most frequent themes in unresolved complaints? What should we fix first?"
      state: active
    - id: prompt_5
      title: Product improvement report
      subtitle: ''
      prompt: "Give me a product improvement report based on the last 1000 complaints."
      state: active
welcome_content:
  welcome_message: Welcome to Complaints Analyser
  description: Retrieve and analyse customer complaints for actionable product improvement insights.
  is_default_message: false
instructions: |
  You are the Complaints Analyser, an AI assistant specialising in customer complaint analysis for product improvement.

  You have access to a complaints database through the globex-complaints toolkit. Use the available tools to retrieve and analyse complaint data.

  ## Your responsibilities:
  - Retrieve complaint records when asked, using get_last_1000_complaints for recent data or read_query for specific queries
  - Use list_tables and describe_tables to understand the data structure before querying
  - Summarise complaints clearly, grouping them by theme, category, or severity where relevant
  - Identify recurring issues and highlight the most impactful problems affecting customers
  - Provide actionable product improvement recommendations based on complaint patterns
  - Answer specific questions about complaints (e.g. by date range, product, category, or customer)

  ## Guidelines:
  - Always be concise, factual, and evidence-based — ground your analysis in the actual data
  - When summarising, highlight the top issues by frequency and severity
  - Frame insights from a product improvement perspective, not just a support perspective
  - If a query returns a large dataset, summarise key trends rather than listing every record
  - Ask clarifying questions if the user's request is ambiguous
----

[cols="1,2", options="header"]
|===
| Field | Meaning

| `kind: native`
| An agent built and run by Orchestrate, as opposed to an external agent it federates to.

| `llm`
| The model backing the agent.

| `style: react_core`
| ReAct-style reasoning: the agent plans, calls a tool, reads the result, and decides what to do next.

| `tools`
| The four toolkit tools the agent is allowed to call. The agent cannot call anything not listed here.

| `starter_prompts`
| The suggested prompts shown in the chat UI. `is_default_prompts: false` replaces the generated ones with your list.

| `welcome_content`
| The heading and description shown before the first message.

| `instructions`
| The system prompt. It tells the agent when to use each tool and how to present results.
|===

Import the agent:

[source,bash,role=execute]
----
orchestrate agents import -f agents/complaints_analyser.yaml
----

Deploy it to make it live:

[source,bash,role=execute]
----
orchestrate agents deploy --name complaints_analyser
----

Importing registers the agent; deploying makes it available to chat with. Re-import after any change to the YAML, then deploy again.

== Test and Validate

List the agents and confirm `complaints_analyser` is deployed:

[source,bash,role=execute]
----
orchestrate agents list
----

Chat with the agent from the CLI:

[source,bash,role=execute]
----
orchestrate chat start -a complaints_analyser -m "Show me a breakdown of complaints by severity."
----

The agent calls `list_tables` and `describe_tables` to inspect the schema, then `read_query` to run the query, and summarises the result. A reply that contains counts by severity confirms the whole chain works: agent to toolkit, toolkit to MCP server, and the connection's OAuth token to Keycloak.
