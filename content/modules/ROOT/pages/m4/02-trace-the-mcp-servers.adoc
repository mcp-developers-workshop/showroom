= Trace Both MCP Servers
:numbered:
:icons: font
:source-highlighter: highlight.js

The same two extensions on both MCP servers, with two extra properties each.

[IMPORTANT]
====
Two repositories, two windows, two pipelines. Push the first before starting the second so both builds run together.
====

== Why these servers need more configuration than the agent

`quarkus.langfuse.otel.span-filter` defaults to `ai-only`, which exports AI spans and their ancestors and drops everything else. The agent produces AI spans, so the default suits it and the previous page left it alone. An MCP server produces none -- its spans are HTTP, MCP and JDBC -- so on the default it would export nothing. Both servers set `span-filter=all`.

Server-side MCP tracing is off by default too. `quarkus.mcp.server.tracing.enabled` defaults to `false`, where the agent's MCP *client* tracing defaults to `true`.

== The orders server

In the `globex-store-mcp` window. This repository has a Maven wrapper:

[source,sh,role="copypaste"]
----
./mvnw quarkus:add-extension -Dextensions="opentelemetry,io.quarkiverse.langfuse:quarkus-langfuse"
----

Add to `src/main/resources/application.properties`:

[source,properties,role="copypaste",subs="attributes+"]
----
# Langfuse
quarkus.langfuse.base-url={langfuse_internal_url}
quarkus.langfuse.public-key={langfuse_public_key}
quarkus.langfuse.secret-key={langfuse_secret_key}
quarkus.langfuse.devservices.enabled=false

# This server has no AI spans of its own, so export everything
quarkus.langfuse.otel.span-filter=all

# Trace the MCP endpoint
quarkus.mcp.server.tracing.enabled=true
----

The same keys as the agent. All three applications report into one Langfuse project, which is what makes their spans one trace rather than three.

[source,sh,role="copypaste"]
----
./mvnw clean compile
----

[source,sh,role="copypaste"]
----
git add .
git commit -m "send traces to Langfuse"
git push
----

Do not wait for the pipeline.

== The complaints server

In the `globex-complaints` window. No Maven wrapper here:

[source,sh,role="copypaste"]
----
mvn quarkus:add-extension -Dextensions="opentelemetry,io.quarkiverse.langfuse:quarkus-langfuse"
----

Add to `src/main/resources/application.properties`:

[source,properties,role="copypaste",subs="attributes+"]
----
# Langfuse
quarkus.langfuse.base-url={langfuse_internal_url}
quarkus.langfuse.public-key={langfuse_public_key}
quarkus.langfuse.secret-key={langfuse_secret_key}
quarkus.langfuse.devservices.enabled=false

# This server has no AI spans of its own, so export everything
quarkus.langfuse.otel.span-filter=all

# Trace both MCP endpoints
quarkus.mcp.server.tracing.enabled=true
quarkus.mcp.server.read.tracing.enabled=true

# Trace JDBC statements
quarkus.datasource.jdbc.telemetry=true
----

Two more lines than the orders server.

`quarkus.mcp.server.read.tracing.enabled` is the named server from Module 3, the read-only one at `/read/mcp`. Named servers are configured independently, so enabling the default server does not enable `read`.

`quarkus.datasource.jdbc.telemetry` gives each SQL statement a span. It is a *build-time* property -- it decides whether the instrumentation is compiled into the image, so changing it later needs another build.

[source,sh,role="copypaste"]
----
mvn clean compile
----

[source,sh,role="copypaste"]
----
git add .
git commit -m "send traces to Langfuse"
git push
----

== Raise another complaint

Same complaint, same way, from the https://globex-web-globex.{openshift_subdomain}/[storefront^].

In Langfuse, open the newest trace. The tool spans that were leaves now have children, and the spans carry three different `service.name` values.

[cols="2,3", options="header"]
|===
| Under | You should see

| the orders tool span
| An MCP server span in `globex-store-mcp`, and under it an outbound HTTP span for the REST call to the Globex Store API.

| the complaints tool span
| An MCP server span in `globex-complaints`, and under it one or more JDBC spans carrying the SQL.
|===

The Globex Store API and PostgreSQL are not instrumented. They appear only as the client spans of the services calling them, which gives their latency but nothing about what happens inside.

== Open a model call

In the same trace, open a span named for a model call. Langfuse shows it as a generation:

* *Input* -- the prompt as actually sent, including the system message and the tool definitions that `quarkus-langchain4j-mcp` generated from each server's `tools/list`. This is assembled at runtime and is not written down anywhere in the source.
* *Output* -- what the model returned.
* *Usage* -- input and output token counts.

Open a tool span and you get the tool name, the arguments the model chose, and the result that came back.

[NOTE]
====
If Input and Output are empty, the agent is missing one of its two extensions. `quarkus-langfuse` only switches on prompt and completion capture when it finds `quarkus-opentelemetry` alongside it.

If cost reads zero while the token counts look right, that is a missing entry in Langfuse's model price table, not missing telemetry.
====

[NOTE]
====
The trace ID does not travel in an HTTP header on the MCP hop. The client puts `traceparent` in the `_meta` field of the JSON-RPC message and the server reads it from there. With `quarkus.mcp.server.tracing.enabled=false` the server still produces an inbound HTTP span but never looks in `_meta`, so that span starts a new trace. In Langfuse that shows up as two unrelated traces rather than one.
====
