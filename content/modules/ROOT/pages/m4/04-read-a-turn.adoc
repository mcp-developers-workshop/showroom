= Read One Turn End to End

:numbered:
:icons: font
:source-highlighter: highlight.js

Nothing to install. Open the trace from the end of the previous page in LangFuse and answer the questions below from the UI.

== The two views

LangFuse renders the same trace twice and you need both.

The *span tree* is the distributed trace: one node per unit of work, nested by caller, each with a start time and a duration, each tagged with the `service.name` it came from.

The *observation detail* is the LLM view. Spans that carry `gen_ai.operation.name` are promoted: a span with `chat` becomes a generation, with input, output, model and token counts as first-class fields; a span with `execute_tool` becomes a tool call, with its arguments and result.

Both are built from the same OTLP spans. Nothing in this workshop sends LangFuse anything else.

== Where the fields come from

Useful when a field is empty and you need to know which end to go and look at.

[cols="2,3", options="header"]
|===
| LangFuse field | Span attribute

| Input
| `gen_ai.prompt`

| Output
| `gen_ai.completion`

| Model
| `gen_ai.request.model`, `gen_ai.response.model`

| Usage
| `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`

| Model parameters
| `gen_ai.request.temperature`, `gen_ai.request.top_p`

| Tool name and arguments
| `gen_ai.tool.name`, `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result`
|===

`gen_ai.prompt`, `gen_ai.completion`, `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result` are the four you switched on in the chart. If Input and Output are empty, those four properties did not reach the running pod.

== The questions

These are the five from the first page of this module, plus three more. Answer each from the LangFuse UI and note how long it takes compared with the log reading you did earlier.

[cols="1,4,3", options="header"]
|===
| | Question | Where

| 1
| Which work belongs to this turn, and nothing else?
| The trace is the answer. Every span in it shares one trace ID, assigned by the agent when the storefront request arrived and carried through every hop.

| 2
| Did the model call the orders tool, the complaints tool, or both -- and in what order?
| The span tree, left to right in time. Tool spans are named for the tool.

| 3
| How long did the model take, how long did the MCP call take, and how long did the database write take?
| Durations on the three nested spans. The database write is a JDBC span inside the complaints server.

| 4
| How many input and output tokens did the turn cost in total?
| Usage, per generation. More than one generation means adding them up -- the trace-level total covers it.

| 5
| What did the second model call receive as input?
| Input on the second generation. The first tool's result is in it, in full, not truncated.

| 6
| What was in the system message, and what tool definitions were sent with it?
| Input on the *first* generation. This is the prompt as sent, after everything the framework added -- not the prompt as written in the source.

| 7
| Why did the model stop when it did?
| `gen_ai.response.finish_reasons` on the generation. `tool_calls` and `stop` mean different things.

| 8
| Which of the three services was the slowest, and was it slow because of its own work or because of something it called?
| Compare a span's duration with the sum of its children's.
|===

Question 6 is the one that is hard to get any other way. The prompt the model receives is assembled at runtime from the `@SystemMessage`, the conversation so far and the tool definitions that `quarkus-langchain4j-mcp` generated from each MCP server's `tools/list`. You wrote one part of that in Module 2. The trace shows all of it.

[NOTE]
====
Cost. LangFuse prices a generation from its own model table, keyed on the model name in the span. If the model you are using is not in that table, cost shows as zero while tokens show correctly -- that is a missing price, not missing telemetry. Quarkus does put a cost estimate of its own on the span, as `gen_ai.client.estimated_cost`, but it is not one of the attributes LangFuse reads.
====

== What the trace does not contain

Two things worth checking for and failing to find.

*The customer.* Search the trace for `asilva`, or for the customer ID the storefront signed in with. It is not there as a field. The agent sends it as the `X-User-Id` header on every MCP call -- the header you built in Module 1 and wired up in Module 2 -- and Quarkus does not put request headers on spans. The one place it may surface is inside `gen_ai.prompt`, if the conversation happens to mention it.

*The token.* The agent's access token and its SPIFFE SVID are not in the trace either, which is the correct outcome rather than a gap. A trace is sent to a third-party backend; credentials do not belong in it.

Both of those are the subject of the summary.
