= Module 4: Observability with LangFuse
:numbered:
:icons: font
:source-highlighter: highlight.js

== Overview & Objectives
One question in the storefront now runs through three Quarkus applications, a model, a REST API and a database. Each application writes its own log, and nothing in one log says which line in another belongs to the same question. This module adds distributed tracing so that one turn is one object you can open.

The backend is LangFuse. It accepts OTLP over HTTP and renders two views of the same data: the span tree, which is the distributed trace, and an LLM view that reads the GenAI span attributes -- prompt, completion, token counts, model. One exporter per service, pointed straight at LangFuse. There is no collector and no separate metrics or logs pipeline in this module.

=== Learning Objectives
* Identify what pod logs cannot answer about a multi-service request, and why.
* Add `quarkus-opentelemetry` to a Quarkus application and export spans over OTLP/HTTP.
* Recognise which telemetry configuration is read at startup and which is fixed when the application is built, and where each has to live in this workshop.
* Read a single agent turn as a trace: which tool the model chose, what it was sent, what came back, and where the time went.
* State what a trace does and does not prove about the identity travelling with a call.

== Architecture & Components
* *Tracing backend:* LangFuse, receiving OTLP/HTTP on its own ingest endpoint
* *Instrumented services:* the agent, the orders MCP server, the complaints MCP server -- `quarkus-opentelemetry` in each
* *Instrumentation already in the extensions:* HTTP server and REST client spans from Quarkus, model-call spans from `quarkus-langchain4j`, MCP client and MCP server spans from the MCP extensions, JDBC spans from Agroal
* *Configuration:* the Helm chart's Secret for the agent, `application.properties` in the repository for the two MCP servers
* *Deployment Pipeline:* GitLab, OpenShift pipeline, ArgoCD -- as in Modules 2 and 3

== Prerequisites
* Modules 1 to 3 completed, with the agent and both MCP servers deployed and working
* A LangFuse instance reachable from the cluster, and a project public key and secret key for it
* The Globex storefront signing in as `asilva`, as used at the end of Module 3

== Lab Agenda
1. Raise one complaint and try to reconstruct the turn from the three pod logs
2. Add OpenTelemetry to the agent and send its spans to LangFuse
3. Do the same on both MCP servers, so one trace covers all three applications
4. Read one turn end to end in LangFuse and answer a fixed set of questions from the UI

== Expected Outcomes
A single trace per storefront question, covering the agent, both MCP servers and the calls they make outwards, with the prompt, the tool choice, the token counts and the per-step latency readable in one place.
