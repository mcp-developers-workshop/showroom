= Module 4: Make MCP Observable
:numbered:
:icons: font
:source-highlighter: highlight.js

== Overview & Objectives

You have built an MCP-based application that works. The question now is how you know what is actually happening when something goes wrong.

An MCP request crosses several components:

....
User
  |
  v
AI Agent  -- calls the model, decides which tool to use
  |
  v
MCP Server
  |
  v
MCP Tool  -- the method the model actually invoked
  |
  v
Backend Service, then the database
....

Logs tell you what each component recorded. They do not show the complete journey of a single request. When a request crosses several services you need to answer questions like:

* Where did the request spend its time?
* Which service was called next?
* Which MCP tool was invoked?
* Where did an error occur?
* What did the agent send to the MCP server, and what came back?

=== Tracing gives you the missing context

Distributed tracing connects related operations into a single trace. Instead of reading separate logs from different pods, you follow one request across the whole application and see its sequence, timing and dependencies.

This matters more for MCP than for a plain `Application -> REST API` call, because the path above has four hops where a plain REST call has one, and the decision about which tool to invoke is made by the model rather than written in the code.

=== Why Langfuse

For AI applications a conventional trace is only part of the picture. You also want the LLM and agent interactions that drive the workflow -- the prompt as sent, the tool the model chose, the token counts.

Langfuse renders both from the same OTLP spans: the span tree, which is the distributed trace, and an LLM view built from the GenAI attributes on those spans. That means one backend and one exporter per service rather than a separate pipeline for each view.

When an MCP workflow fails or behaves unexpectedly, you should be able to follow what happened rather than guess from individual logs.

== Architecture & Components
* *Tracing backend:* Langfuse, receiving OTLP/HTTP
* *Instrumented services:* the agent and both MCP servers, with `quarkus-opentelemetry` and `quarkus-langfuse` in each
* *Instrumentation already present:* HTTP and REST client spans from Quarkus, model-call spans from `quarkus-langchain4j`, MCP client and server spans from the MCP extensions, JDBC spans from Agroal
* *Configuration:* `application.properties` in each of the three repositories
* *Deployment Pipeline:* GitLab, OpenShift pipeline, ArgoCD -- as in Modules 2 and 3

== Prerequisites
* Modules 1 to 3 completed, with the agent and both MCP servers deployed and working
* A Langfuse instance on the cluster, with a project public key and secret key -- provided as workshop variables
* The Globex storefront signing in as `asilva`, as at the end of Module 3

== Lab Agenda
1. Add distributed tracing to the agent and send its traces to Langfuse
2. Do the same on both MCP servers, so one trace covers all three applications
3. Follow one MCP request across the agent, both MCP servers and the services behind them

== Expected Outcomes
One trace per storefront question, covering the agent, both MCP servers and the calls they make outwards, with the prompt, the tool choice, the token counts and the per-step latency in one place.
