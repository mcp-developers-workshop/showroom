= Summary
:numbered:
:icons: font
:source-highlighter: highlight.js

You took three applications that each logged only their own work and made one storefront question into one trace:

* Added `quarkus-opentelemetry` and `quarkus-langfuse` to the agent, with the Langfuse address and project keys in `application.properties`.
* Added the same pair to both MCP servers, plus `span-filter=all` because neither produces AI spans of its own, the server-side MCP tracing property, and JDBC tracing on the complaints server.
* Followed one request from the agent through both MCP servers to the Globex Store API and the database.

Logs show what each component recorded. A trace connects those records into one request, with the sequence, the time spent in each operation, the MCP tools that were called, their arguments and results, and the model calls driving the whole thing.

You wrote no code. Two extensions and a handful of properties per application was enough, because `quarkus-langchain4j`, the MCP extensions and Agroal already contain the instrumentation -- it produces nothing until an OpenTelemetry SDK is on the classpath to receive it. `quarkus-langfuse` did the rest: you never configured an OTLP endpoint, a protocol or an authentication header, because it derives the ingestion URL from `quarkus.langfuse.base-url` and turns on the four LangChain4j content properties that otherwise default to off.

Two things to remember:

*Build-time and runtime properties are not interchangeable.* `quarkus.datasource.jdbc.telemetry` decides whether the instrumentation is compiled into the image, so changing it needs a rebuild. `quarkus.langfuse.base-url` is read at boot, so changing it needs a restart.

*The trace ID is carried by the caller, not by the platform.* Over HTTP it travels as a `traceparent` header. Over MCP it travels in the `_meta` field of the JSON-RPC message, because at that layer MCP is not HTTP-shaped. A service that does not look for it starts a new trace instead of joining the existing one, which is why a propagation failure shows up in Langfuse as two unrelated traces rather than as an error.

The gap Module 3 left is still open. The MCP servers believe the agent about which customer is asking, because `X-User-Id` is a claim rather than proof. Tracing does not change that, and the header is not on any span, so the trace does not record the customer at all.
