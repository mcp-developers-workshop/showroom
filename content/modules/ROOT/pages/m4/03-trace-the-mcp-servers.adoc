= Trace Both MCP Servers

:numbered:
:icons: font
:source-highlighter: highlight.js

The same extension on both MCP servers, with two differences from the agent.

The first is where the configuration goes. Neither MCP server has a chart you can edit -- only `globex-complaint-agent-helm` is in GitLab -- and neither deployment mounts a config Secret. Their `application.properties` is built into the image, as you saw when you added OIDC in Module 3. So the extension and its configuration go in the same commit, one pipeline builds both, and the pod that comes up has everything. There is no ordering problem on this page and no restart to do.

The second is that the server side of the MCP tracing is off by default. `quarkus.mcp.server.tracing.enabled` defaults to `false`, which the agent's own MCP client does not -- its tracing is on as soon as OpenTelemetry is present.

[IMPORTANT]
====
Two repositories, two windows, two pipelines. Push the first before you start the second so both builds run at the same time.
====

== The orders server

In the `globex-store-mcp` window. This repository has a Maven wrapper:

[source,sh,role="copypaste"]
----
./mvnw quarkus:add-extension -Dextensions="opentelemetry"
----

Add to `src/main/resources/application.properties`:

[source,properties,role="copypaste",subs="attributes+"]
----
# Export traces to LangFuse
quarkus.otel.exporter.otlp.traces.protocol=http/protobuf
quarkus.otel.exporter.otlp.traces.endpoint=https://{langfuse_host}/api/public/otel
quarkus.otel.exporter.otlp.traces.headers=Authorization=Basic <the base64 string from the previous page>

# Trace the MCP endpoint
quarkus.mcp.server.tracing.enabled=true
----

The same base64 credential as the agent. All three services report into one LangFuse project, which is what makes them one trace rather than three.

[WARNING]
====
This commits a LangFuse secret key to the application repository, where it is also baked into the image. The agent at least kept it in a chart. There is no better option here without adding a Secret and a config mount to a chart you do not have access to, and it is called out rather than hidden.
====

[source,sh,role="copypaste"]
----
./mvnw clean compile
----

[source,sh,role="copypaste"]
----
git add .
git commit -m "export traces to LangFuse"
git push
----

Do not wait for the pipeline.

== The complaints server

In the `globex-complaints` window. No Maven wrapper here, so plain `mvn`:

[source,sh,role="copypaste"]
----
mvn quarkus:add-extension -Dextensions="opentelemetry"
----

Add to `src/main/resources/application.properties`:

[source,properties,role="copypaste",subs="attributes+"]
----
# Export traces to LangFuse
quarkus.otel.exporter.otlp.traces.protocol=http/protobuf
quarkus.otel.exporter.otlp.traces.endpoint=https://{langfuse_host}/api/public/otel
quarkus.otel.exporter.otlp.traces.headers=Authorization=Basic <the base64 string from the previous page>

# Trace both MCP endpoints
quarkus.mcp.server.tracing.enabled=true
quarkus.mcp.server.read.tracing.enabled=true

# Trace JDBC statements
quarkus.datasource.jdbc.telemetry=true
----

Two extra lines compared with the orders server.

`quarkus.mcp.server.read.tracing.enabled` is the named server from Module 3 -- the read-only one at `/read/mcp` that Module 5 uses. Named servers are configured independently, so switching on the default server does not switch on `read`.

`quarkus.datasource.jdbc.telemetry` wraps the datasource so each statement gets a span. This one is a *build-time* property: it decides whether the instrumentation is in the image at all, so it cannot be changed later without another build. That is a second reason the configuration belongs in the repository here rather than anywhere else.

[source,sh,role="copypaste"]
----
mvn clean compile
----

[source,sh,role="copypaste"]
----
git add .
git commit -m "export traces to LangFuse"
git push
----

== Raise another complaint

Same complaint, same way, from the https://globex-web-globex.{openshift_subdomain}/[storefront^].

In LangFuse, open the newest trace. The tool spans that were leaves on the previous page now have children, and the spans carry three different `service.name` values.

What to look for, depending on which tools the model chose:

[cols="2,3", options="header"]
|===
| Under | You should see

| the orders tool span
| An MCP server span in `globex-store-mcp`, and under it an outbound HTTP span for the REST call to the Globex Store API.

| the complaints tool span
| An MCP server span in `globex-complaints`, and under it one or more JDBC spans carrying the SQL statement.
|===

The Globex Store API and Postgres are not instrumented and never will be in this workshop. They appear as the client spans of the services that call them, which is enough to see their latency and not enough to see inside them.

[NOTE]
====
The trace ID does not travel in an HTTP header on the MCP hop. The MCP client puts `traceparent` into the `_meta` field of the JSON-RPC message, and the MCP server reads it from there. That is why the server-side property matters: with `quarkus.mcp.server.tracing.enabled=false` the server still produces an inbound HTTP span, but it never looks in `_meta`, so that span starts a new trace instead of joining yours. A missing MCP property and a missing extension look the same from the agent's side; they look different in LangFuse, where you get two unrelated traces rather than one.
====
