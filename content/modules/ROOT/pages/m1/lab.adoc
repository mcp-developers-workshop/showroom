== Generate the MCP Server with IBM Bob

The Globex store exposes a REST API described by an OpenAPI specification. Instead of writing the MCP server by hand, you ask Bob to build a Quarkus MCP server that wraps that API and exposes one tool.

This is the brownfield pattern: the existing API is untouched, and the MCP server sits in front of it.

=== Review the OpenAPI specification

[source,bash,role=execute,subs="attributes"]
----
https://globex-store.{openshift_subdomain}/q/openapi
----

=== Prompt IBM Bob

In IBM Bob, make sure the `globex-store-mcp` folder is your working context, then enter the following prompt:

[source,bash,role=execute,subs="attributes"]
----
Within the globex-store-mcp folder, Download the openapi spec document located at https://globex-store.{openshift_subdomain}/q/openapi . Create a mcp server called "GlobexStoreMcpServer" which exposes a tool called "getOrdersByCustomerId" to get the orders for a given customerId. The tool implementation should connect to the API described in the openAPI spec document and return the API response. The mcp server should use the streamable http transport. Use the appropriate quarkus extension for the mcp server.
----

=== Approve Bob's tasks

Bob breaks the request into tasks and asks for confirmation before running them -- downloading the specification, adding the Quarkus extension, creating files, running commands. Expect several prompts.

Read each question, click *Approve*, and keep going until Bob reports that it has finished.

[NOTE]
====
The questions tell you which extension and project layout Bob has settled on.
====

=== What the prompt specifies

[cols="1,2", options="header"]
|===
| Instruction | Effect

| Download the OpenAPI spec
| Bob generates the client from the actual contract instead of guessing endpoint shapes.

| Expose a tool to get orders for a given `customerId` 
| One narrow tool rather than a mapping of every REST endpoint.

| Connect to the API described in the spec and return the response
| The MCP server wraps the API; it does not reimplement the logic.

| Use the streamable HTTP transport
| Needed for the server to be reachable once deployed on OpenShift.

| Use the appropriate Quarkus extension
| Points Bob at the Quarkus MCP server extension instead of a hand-rolled protocol implementation.
|===

=== Review Bob's summary

Bob builds and tests the project, then prints a summary of what was created. Check it against what you asked for:

* A Quarkus project inside the `globex-store-mcp` folder.
* The `quarkus-mcp-server-http` extension in the build file.
* A `getOrdersByCustomerId` tool that takes a customer ID and returns that customer's orders.
* A client generated from the downloaded OpenAPI specification.
* Configuration selecting the streamable HTTP transport.
* A passing build and test run.

If something is missing, tell Bob in a follow-up prompt and let it correct the project before continuing.

== Shape the Data Returned by the Tool

The tool currently returns whatever the Globex Store API returns, including shipping addresses and prices that an agent does not need to answer a question about order history.

Next you trim and reshape the payload so the tool returns only the required fields.

=== Prompt IBM Bob

[source,bash,role=execute,subs="attributes"]
----
Change the contents of the JSON data returned by the mcp server. The orders in the history should not contain the shipping address. The product line items should not contain the price, but they should contain the product code, quantity and the product name. This might need additional calls to the backend api described in https://globex-store.{openshift_subdomain}/q/openapi
----

As before, read Bob's questions and click *Approve*.

=== What changes

[cols="1,1,2", options="header"]
|===
| Field | Action | Reason

| Shipping address
| Removed
| Personally identifiable information, not needed to describe an order.

| Line item price
| Removed
| Commercially sensitive, not needed for an order-history question.

| Product code
| Kept
| Identifies the item.

| Quantity
| Kept
| Describes what was ordered.

| Product name
| Added
| Human-readable label for the product code.
|===

[NOTE]
====
The orders endpoint returns product codes, not names, so Bob has to call a second endpoint from the same OpenAPI specification to resolve each code into a product name. That is what the last sentence of the prompt allows for.
====

=== Verify the new response shape

Bob rebuilds and re-tests. Once dev mode has restarted, invoke the tool again from the Dev UI:

[source,text,role="copypaste"]
----
http://localhost:8080/q/dev-ui/quarkus-mcp-server-http/tools
----

Check the returned JSON:

* No shipping address in the order history.
* No price on any line item.
* Every line item has a product code, a quantity, and a product name.

== Pass the Customer Identifier as an HTTP Header

The tool takes `customerId` as a parameter, which means the model supplies it. Next you move it to an HTTP header on the MCP request, so the caller sets it and the model never sees it.

=== Prompt IBM Bob

[source,text,role="copypaste"]
----
The 'getOrders' tool in src/main/java/org/globex/mcp/server/GlobexStoreMcpServer.java takes the customerId as parameter. Change the implementation so that the customerId is passed as a HTTP header. The name of the header is 'X-User-Id'. Throw an exception if the header is not present or is empty.
----

Read Bob's questions and click *Approve*.

=== What changes

[cols="1,2", options="header"]
|===
| Change | Effect

| `customerId` removed from the tool signature
| The identifier is no longer part of the tool contract the model sees.

| Read from the `X-User-Id` header
| The identity travels on the transport, set by the caller.

| Exception when the header is missing or empty
| No header means no data, rather than a default or an unfiltered result set.
|===

[NOTE]
====
`X-User-Id` is unverified -- the caller can set it to anything. It gets replaced with a verified identity later in the workshop.
====

=== Verify the change

Once dev mode restarts, open the Dev UI tools page:

[source,text,role="copypaste"]
----
http://localhost:8080/q/dev-ui/quarkus-mcp-server-http/tools
----

Confirm that the tool no longer lists `customerId` as an input parameter.

=== Test the header with MCP Inspector

Leave dev mode running and open a second terminal.

Start the Inspector:

[source,sh,role="copypaste"]

----

It starts a local proxy and prints a URL for the UI (default `http://localhost:6274`) and the inspector is opened in the browser.

The landing page lists the servers the Inspector knows about, all disconnected:

[NOTE]
====
The printed URL carries an `MCP_INSPECTOR_API_TOKEN` query parameter. Use the URL exactly as printed -- opening `http://localhost:6274` on its own does not authenticate against the proxy.

Click *Add Servers* -> *Add Manually* and fill in the dialog:

==== Connect to the server

A card for `order-mcp-local` appears alongside the examples, marked *Disconnected*:

image::m1/mcp-inspector-server-added.png[]

The card turns green and reads *Connected*, the server's name (`GlobexStoreMcpServer`) appears in the top-left, the negotiated protocol version is shown on the card, and a *Tools* tab appears next to *Servers*:

image::m1/mcp-inspector-connected.png[]

==== Check the tool schema

Open the *Tools* tab. The left-hand panel lists the tools the server advertises -- just `getOrdersByCustomerId`:

image::m1/mcp-inspector-tools-list.png[]

Click the tool to see its details:

image::m1/mcp-inspector-tool-detail.png[]

The panel shows the description and an *Execute Tool* button, and nothing else. There are no input fields, because the tool no longer declares any parameters -- the customer ID comes from the `X-User-Id` header instead.

==== Call the tool without the header

Click *Execute Tool*.

The call fails with *Tool Call Failed* / *Internal error*, because the tool throws when `X-User-Id` is missing:

image::m1/mcp-inspector-tool-error.png[]

[NOTE]
====
The *Network* panel on the right records the request as `200 OK`. The HTTP request itself succeeded; the failure is carried inside the MCP response, which is how tool errors are reported.
====

==== Add the header

Go back to the *Servers* tab and click *Settings* on the `order-mcp-local` card:

image::m1/mcp-inspector-card-settings.png[]

The *Server Settings* dialog opens on the *Options* section. Scroll to the bottom and expand *Custom Headers*:

image::m1/mcp-inspector-server-settings.png[]

Click *+ Add Header* and fill in the two fields:

[cols="1,2", options="header"]
|===
| Field | Value

| Header name
| `X-User-Id`

| Header value
| `asilva`
|===

image::m1/mcp-inspector-custom-header.png[]

Close the dialog.

[IMPORTANT]
====
Custom headers only take effect on a new connection, and the Inspector does not pick them up on a reconnect alone. Reload the browser page, then connect to `order-mcp-local` again as you did earlier.
====

==== Call the tool with the header

Go to the *Tools* tab, select `getOrdersByCustomerId`, and click *Execute Tool*.

The call succeeds and the *Results* panel shows the shaped order history for `asilva`:

image::m1/mcp-inspector-tool-result.png[]

Check the JSON against the two changes you made:

* No shipping address on any order.
* No price on any line item, and every line item has `productCode`, `productName` and `quantity`.

The tool took no arguments. The customer whose orders came back was determined entirely by the `X-User-Id` header, which the model never sees and cannot change.

The deployed server reads `X-User-Id` exactly as the local one does, so it needs the same header. On the `order-mcp-remote` card, click *Settings*, expand *Custom Headers*, click *+ Add Header* and add:

[cols="1,2", options="header"]

| Header name
| `X-User-Id`

| Header value
| `asilva`
|===

=== Call the tool

Turn off the toggle on the `order-mcp-local` card to disconnect from dev mode, then connect to `order-mcp-remote`.

Open the *Tools* tab, select `getOrdersByCustomerId` and click *Execute Tool*.

The result matches what the local server returned: the same orders for `asilva`, with no shipping address and no prices. The code you wrote in Bob is now running on the cluster.

[NOTE]
====
Leave both entries in place. `order-mcp-local` points at dev mode on your VM, `order-mcp-remote` at the deployed route, which makes it easy to compare the two as you change the server in later modules.
====

[IMPORTANT]
====
The deployed server is not secured. The route is open, and anything that can reach it can set `X-User-Id` to any value and read that customer's orders. You fix this later in the workshop.
====

== Summary

You built an MCP server over an existing REST API and got it running on OpenShift:

* Generated a Quarkus MCP server from the Globex Store OpenAPI specification with IBM Bob, exposing one tool over the streamable HTTP transport.
* Trimmed the tool's response to the fields an agent needs -- no shipping address, no prices, product names resolved from a second endpoint.
* Moved the customer identifier out of the tool signature and onto the `X-User-Id` HTTP header, so the caller sets it and the model cannot.
* Verified all three changes with the MCP Inspector against dev mode.
* Pushed to GitLab, watched the build produce an image and the deployment roll it out, and ran the same tool call against the deployed route.

Three things carried the design: the API was left untouched and wrapped, the tool was kept narrow and its payload minimised, and the identity was moved off the model's contract. The remaining gap is that nothing verifies `X-User-Id`.
