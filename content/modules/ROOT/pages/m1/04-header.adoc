= Pass the Customer Identifier as an HTTP Header
:numbered:
:icons: font
:source-highlighter: highlight.js

The tool takes `customerId` as a parameter, which means the model supplies it. Next you move it to an HTTP header on the MCP request, so the caller sets it and the model never sees it.

== Prompt IBM Bob

[source,text,role="copypaste"]
----
The 'getOrdersByCustomerId' tool GlobexStoreMcpServer.java takes the customerId as parameter. Change the implementation so that the customerId is passed as a HTTP header. The name of the header is 'X-User-Id'. Throw an exception if the header is not present or is empty.
----

Read Bob's questions and click *Approve*.

== What changes

[cols="1,2", options="header"]
|===
| Change | Effect

| `customerId` removed from the tool signature
| The identifier is no longer part of the tool contract the model sees.

| Read from the `X-User-Id` header
| The identity travels on the transport, set by the caller.

| Exception when the header is missing or empty
| No header means no data, rather than a default or an unfiltered result set.
|===

[NOTE]
====
`X-User-Id` is unverified -- the caller can set it to anything. It gets replaced with a verified identity later in the workshop.
====

== Verify the change

Once dev mode restarts, open http://localhost:8080/q/dev-ui/quarkus-mcp-server-http/tools[the Dev UI tools page^] and click the tool name:

image::m1/devui-getorders-no-parameters.png[link=self,window=_blank]

The tool now declares no parameters. The customer identifier is no longer part of the contract the model sees, so there is nothing for it to supply or change.

== Test the header with MCP Inspector

The Dev UI does not let you set request headers, so use the *MCP Inspector* to check the header handling. The Inspector is a standalone MCP client with a browser UI, so it connects to your server the same way an agent would.

Leave dev mode running and open a second terminal.

Start the Inspector:

[source,sh,role="copypaste"]
----
npx @modelcontextprotocol/inspector
----

It starts a local proxy and prints a URL for the UI (default `http://localhost:6274`) and the inspector is opened in the browser.

The landing page lists the servers the Inspector knows about, all disconnected:

image::m1/mcp-inspector-servers.png[link=self,window=_blank]

=== Add your server

The three entries on the page are the Inspector's built-in examples. Add your own.

Click *Add Servers* -> *Add Manually* and fill in the dialog:

image::m1/mcp-inspector-add-server.png[link=self,window=_blank]

[cols="1,2", options="header"]
|===
| Field | Value

| Server ID
| `order-mcp-local`

| Transport
| `streamable-http`

| URL
| `\http://localhost:8080/mcp`
|===

Click *Add*.


=== Connect to the server

A card for `order-mcp-local` appears alongside the examples, marked *Disconnected*:

image::m1/mcp-inspector-server-added.png[link=self,window=_blank]

Click the *Disconnected* toggle on that card to connect.

The card turns green and reads *Connected*, the server's name (`GlobexStoreMcpServer`) appears in the top-left, the negotiated protocol version is shown on the card, and a *Tools* tab appears next to *Servers*:

image::m1/mcp-inspector-connected.png[link=self,window=_blank]

=== Check the tool schema

Open the *Tools* tab. The left-hand panel lists the tools the server advertises -- just `getOrdersByCustomerId`:

image::m1/mcp-inspector-tools-list.png[link=self,window=_blank]

Click the tool to see its details:

image::m1/mcp-inspector-tool-detail.png[link=self,window=_blank]

The panel shows the description and an *Execute Tool* button, and nothing else. There are no input fields, because the tool no longer declares any parameters -- the customer ID comes from the `X-User-Id` header instead.

=== Call the tool without the header

Click *Execute Tool*.

The call fails with *Tool Call Failed* / *Internal error*, because the tool throws when `X-User-Id` is missing:

image::m1/mcp-inspector-tool-error.png[link=self,window=_blank]

[NOTE]
====
The *Network* panel on the right records the request as `200 OK`. The HTTP request itself succeeded; the failure is carried inside the MCP response, which is how tool errors are reported.
====

=== Add the header

Go back to the *Servers* tab and click *Settings* on the `order-mcp-local` card:

image::m1/mcp-inspector-card-settings.png[link=self,window=_blank]

The *Server Settings* dialog opens on the *Options* section. Scroll to the bottom and expand *Custom Headers*:

image::m1/mcp-inspector-server-settings.png[link=self,window=_blank]

Click *+ Add Header* and fill in the two fields:

[cols="1,2", options="header"]
|===
| Field | Value

| Header name
| `X-User-Id`

| Header value
| `asilva`
|===

image::m1/mcp-inspector-custom-header.png[link=self,window=_blank]

Close the dialog.

[IMPORTANT]
====
Custom headers only take effect on a new connection, and the Inspector does not pick them up on a reconnect alone. Reload the browser page, then connect to `order-mcp-local` again as you did earlier.
====

=== Call the tool with the header

Go to the *Tools* tab, select `getOrdersByCustomerId`, and click *Execute Tool*.

The call succeeds and the *Results* panel shows the shaped order history for `asilva`:

image::m1/mcp-inspector-tool-result.png[link=self,window=_blank]

Check the JSON against the two changes you made:

* No shipping address on any order.
* No price on any line item, and every line item has `productCode`, `productName` and `quantity`.

The tool took no arguments. The customer whose orders came back was determined entirely by the `X-User-Id` header, which the model never sees and cannot change.
