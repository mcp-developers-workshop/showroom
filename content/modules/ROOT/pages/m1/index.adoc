== Overview & Objectives

While building such agents and AI systems in an enterprise environment, you will use a mix of internal custom-built MCP servers built within your organization, and external MCP servers to access other 3rd party services such as ticketing and order management systems. 

This module guides you through building a a Globex MCP server from an existing Globex Store API using AI-driven development with IBM Bob.  _Glo, the agent_ will use this MCP server to access the Globex Store API to retrieve a user's order history. 

A few architectural considerations while building an MCP server:

* *Intentional Toolbox:* Expose minimal, intent-driven tools via MCP Servers
expose tools to fetch a user's order history 
* *Data massaging:* Restrict scope of data retrieved from API before sending to agent.
* *Confidential Data:* Use MCP headers for confidential info and identifiers (e.g. userId)

== Building your own MCP Servers

There are two common ways to introduce MCP into an enterprise environment, and this workshop uses both.

=== Brownfield

In most enterprises, you're not starting from scratch. You already have APIs and existing services. In these cases, you can introduce a standalone MCP server in front of those APIs. The MCP server defines which capabilities to expose as tools and how the data is shaped for the AI application. The underlying API or service does not need to change.

The orders server is brownfield: it sits in front of the existing Globex Store REST API.

image::m1/mcp-brownfield.png[link=self,window=_blank,width=60%]

=== Greenfield

When you're building something new, you can design the application for AI support from the beginning. The MCP server and the application's REST endpoints can be developed together as part of the same application.

The complaints server is greenfield: it accesses the Globex database directly, with the MCP tools designed alongside the application logic.

image::m1/mcp-greenfield.png[link=self,window=_blank,width=60%]

From Glo's perspective, both approaches look the same: it discovers MCP tools and invokes them. What happens behind the MCP server is an implementation detail.

NOTE: In this workshop, you build the brownfield Orders MCP server. The greenfield complaints server is pre-deployed so that you can use it in the later modules without having to build a second server.

== Learning Objectives

By the end of this module, you will:

* Generate a Quarkus MCP server from an OpenAPI specification using IBM Bob.
* Expose a single defined tool over the streamable HTTP transport instead of mapping every REST endpoint.
* Apply data minimization by returning only the fields the agent needs, and dropping personal data such as addresses, prices etc that usually existing APIs include.
* Move confidential identifier such as _*userId*_ out of the tool's parameters and onto an HTTP header, so the caller sets it and the model never sees it.
* Test an MCP server with the Quarkus Dev UI and with the MCP Inspector.
* Deploy the server to OpenShift by pushing to GitLab and letting ArgoCD sync it.

== Expected Outcomes

By the end of this module, you will have a Quarkus MCP server running on OpenShift that wraps the existing Globex Store API, exposes a single focused tool, returns only the data the agent needs, and takes the customer identity from an HTTP header rather than from the model.
