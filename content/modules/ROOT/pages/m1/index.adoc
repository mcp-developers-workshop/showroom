== Overview & Objectives

While building such agents and AI systems in an enterprise environment, you will use a mix of internal custom-built MCP servers built within your organization, and external MCP servers to access other 3rd party services such as ticketing and order management systems. 

This module guides you through building a a Globex MCP server from an existing Globex Store API using AI-driven development with IBM Bob.  _Glo, the agent_ will use this MCP server to access the Globex Store API to retrieve a user's order history. 

A few architectural considerations while building an MCP server:

* *Intentional Toolbox:* Expose minimal, intent-driven tools via MCP Servers
expose tools to fetch a user's order history 
* *Data massaging:* Restrict scope of data retrieved from API before sending to agent.
* *Confidential Data:* Use MCP headers for confidential info and identifiers (e.g. userId)

== Building your own MCP Servers

A custom MCP server is built one of two ways, and the workshop uses both.

*Brownfield* wraps a system that already exists and is not going to change. The server sits in front of it and translates between the protocol and endpoints designed for something else -- a REST API, a SOAP service, a mainframe transaction, a vendor SDK. The existing endpoints are not the tools: which ones to expose, under what name, returning how much, is the work. The orders server you build in this module is brownfield. The Globex Store REST API is untouched and never learns that anything is wrapping it, which is the ordinary enterprise case.

image::m1/mcp-brownfield.png[link=self,window=_blank]

*Greenfield* writes the server and the logic behind it together, with the tools as the system's primary interface. There is no contract to preserve, so tool names, arguments and payloads are designed for a model from the start. The complaints server you connect in Module 2 is greenfield -- it was built as an MCP server and reaches the Globex database directly, with no REST API in between.

image::m1/mcp-greenfield.png[link=self,window=_blank]

Either way the client cannot tell the difference. Glo, the agent you build in Module 2 -- sees a list of tools and calls them; whether a tool runs SQL or forwards to a legacy endpoint is the server's business.


=== Learning Objectives
* Generate a Quarkus MCP server from an OpenAPI specification using IBM Bob.
* Expose a single narrow tool over the streamable HTTP transport instead of mapping every REST endpoint.
* Apply data minimization: return only the fields the agent needs, and drop personal and commercial data the API happens to include.
* Move a confidential identifier out of the tool's parameters and onto an HTTP header, so the caller sets it and the model never sees it.
* Test an MCP server with the Quarkus Dev UI and with the MCP Inspector.
* Deploy the server to OpenShift by pushing to GitLab and letting ArgoCD sync it.

== Architecture & Components
* *AI code assistant:* IBM Bob
* *Framework:* Quarkus with the `quarkus-mcp-server-http` extension
* *Backend system:* the Globex Store REST API, described by an OpenAPI specification
* *Transport:* streamable HTTP
* *Deployment target:* Red Hat OpenShift, via GitLab and ArgoCD
* *Testing:* Quarkus Dev UI and MCP Inspector

== Prerequisites
* A workshop VM with IBM Bob installed
* An account on the workshop GitLab instance
* Access to the workshop OpenShift cluster and its ArgoCD instance

[NOTE]
====
There is nothing to install. Quarkus runs through the Maven wrapper in the project, the Quarkus tooling reaches Bob over MCP through `jbang`, and the MCP Inspector runs through `npx`.
====

== Lab Agenda
1. Set up the workshop environment: sign in to GitLab, open IBM Bob, give it the Quarkus tooling, and clone the repository
2. Generate the MCP server from the Globex Store OpenAPI specification and confirm the tool in the Dev UI
3. Shape the data the tool returns, dropping the shipping address and line item prices
4. Pass the customer identifier as the `X-User-Id` HTTP header and test it with the MCP Inspector
5. Commit and deploy: push to GitLab and watch ArgoCD roll it out
6. Test the deployed MCP server over its public route

== Expected Outcomes
A Quarkus MCP server running on OpenShift that wraps the existing Globex Store API, publishes one tool, returns only the fields an agent needs, and takes the customer identity from a header rather than from the model. Module 2 gives that tool to an agent; nothing yet verifies the header, which is the gap Module 3 closes.
