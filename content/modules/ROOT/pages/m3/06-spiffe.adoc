== Why the client secret is not enough

Enabling OIDC authentication across the agent and the MCP servers left the agent holding a Keycloak identity of its own, and both servers accepting it. That identity is a client ID and a client secret.

Keycloak checks that the secret matches the one it holds for that client -- nothing more. It cannot tell whether the caller is your agent or a laptop that copied the secret out of the Git repository you put it in on the last page.

That is the weakness of any shared secret: it proves *what you have*, not *who you are*. And because changing it means changing it everywhere at once, it is rarely changed at all.

== What SPIFFE is

SPIFFE is a standard for giving a workload an identity based on what it actually is and where it actually runs, instead of a secret it carries.

Three terms cover it:

[cols="1,3", options="header"]
|===
| Term | What it means

| Trust domain
| The boundary that issues identities -- in practice, your cluster.

| SPIFFE ID
| The name of one workload, written as a URI: `spiffe://globex.com/ns/globex-complaint-agent/sa/globex-complaint-agent`. A username for a pod rather than a person.

| SVID
| The credential that proves the SPIFFE ID, as an X.509 certificate or a JWT. It is valid for minutes, not forever.
|===

The agent stores none of this. It asks for an SVID when it needs one and gets a fresh one each time.

== What it takes to run it

The identity has to come from something that can actually verify the claim, and that is the platform the workload runs on. SPIRE is the implementation:

* A *SPIRE server* -- the certificate authority for the trust domain.
* A *SPIRE agent* on every node. When a pod asks for an identity, the agent asks the kubelet what that pod really is -- its namespace, its service account, its image -- and only then issues the SVID. That check is *attestation*, and it is what a secret cannot do.
* A *registration entry* per workload, mapping those pod properties to a SPIFFE ID. This is the one piece a human writes.
* A consumer that trusts the trust domain. Here that is Keycloak, which has to accept an SVID where it currently expects a client secret.

The workload talks to its node's SPIRE agent over a local Unix socket, so there is no credential to put in a chart, in Git, or in an environment variable, and nothing to rotate on a schedule.

== What you build on this page

A SPIRE agent attests the agent pod and issues it a short-lived JWT-SVID. The agent sends that SVID to Keycloak in place of the client secret, as a *client assertion*. Keycloak matches it to the Keycloak client the agent already uses and issues the same access token as before -- so the MCP servers need no change, and both `quarkus.oidc-client.*` blocks from the last page stay. What goes away is the secret in `values.yaml`.

== What is already on the cluster

The platform half is installed for you. The *Zero Trust Workload Identity Manager* operator runs SPIRE on OpenShift through four custom resources:

[cols="1,2", options="header"]
|===
| Resource | What it does

| `ZeroTrustWorkloadIdentityManager`
| Sets the trust domain (`globex.com`) and cluster name for everything below.

| `SpireServer`
| The CA for the trust domain. JWT-SVIDs it issues are valid for *five minutes*.

| `SpireAgent`
| One per node. Attests pods using the Kubernetes projected service account token, then answers Workload API requests.

| `SpiffeCSIDriver`
| Publishes the SPIRE agent's Unix socket into a pod as a volume, so the workload can reach the Workload API without a host mount.
|===

Keycloak is configured for it too -- the `client-auth-federated` and `spiffe` features are enabled on the server, and the `internal` realm carries:

* An identity provider named `spiffe`, of type `CLIENT_ASSERTION`, pointing at the trust domain `spiffe://globex.com` and SPIRE's bundle endpoint. This is what lets Keycloak verify an SVID it is handed.
* A client whose `clientAuthenticatorType` is `federated-jwt` rather than `client-secret`, with the agent's SPIFFE ID recorded on it as `jwt.credential.sub`.

So Keycloak will not look up a secret for this client at all. It verifies the SVID's signature against the trust domain, reads the subject, and checks it matches the SPIFFE ID on the client.

== How the agent gets its SVID

The agent does not call the Workload API itself. A helper does it, and leaves the token on disk where Quarkus can read it:

....
SPIRE agent (node)
   |  Unix socket, mounted by the CSI driver
   v
spiffe-helper (init container)   -- fetches the first SVID before the agent starts
spiffe-helper (sidecar)          -- renews it, every few minutes, for the life of the pod
   |
   v
/svids/jwt.token   <-- shared emptyDir, read by the agent container
....

The init container matters: a JWT-SVID lasts five minutes, so the agent must not start before one exists, and must never be left holding an expired one.

== Add the client assertion type filter

One Java class, and it exists for a protocol mismatch.

When Quarkus authenticates with a JWT instead of a secret, it sends `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, which is what RFC 7523 specifies. Keycloak's SPIFFE support expects `urn:ietf:params:oauth:client-assertion-type:jwt-spiffe`. Nothing in configuration bridges that, so the request body is rewritten on the way out.

[source,sh,role="copypaste"]
----
mkdir -p src/main/java/org/globex/retail/ai/complaint/spiffe
touch src/main/java/org/globex/retail/ai/complaint/spiffe/SpiffeClientAssertionTypeRequestFilter.java
----

[source,java,role="copypaste"]
----
package org.globex.retail.ai.complaint.spiffe;

import io.quarkus.arc.Unremovable;
import io.quarkus.oidc.common.OidcRequestFilter;
import io.smallrye.mutiny.Uni;
import io.vertx.mutiny.core.buffer.Buffer;
import jakarta.annotation.Priority;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
@Priority(500)
@Unremovable
public class SpiffeClientAssertionTypeRequestFilter implements OidcRequestFilter {

    private static final String DEFAULT_ASSERTION_TYPE =
        "urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer";
    private static final String SPIFFE_ASSERTION_TYPE =
        "urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-spiffe";

    @Override
    public Uni<Void> filter(OidcRequestFilterContext context) {
        Buffer body = context.requestBody();
        if (body != null) {
            String bodyString = body.toString();
            if (bodyString.contains(DEFAULT_ASSERTION_TYPE)) {
                context.requestBody(Buffer.buffer(bodyString.replace(DEFAULT_ASSERTION_TYPE, SPIFFE_ASSERTION_TYPE)));
            }
        }
        return Uni.createFrom().voidItem();
    }
}
----

The values are URL-encoded because this rewrites a form-encoded body, not a header. `@Unremovable` keeps Quarkus from discarding a bean nothing injects.

An `OidcRequestFilter` applies to every outgoing OIDC request the application makes, so one class covers both OIDC clients. This is the only Java change on this page -- the two auth providers from page 05 are untouched, and no extension is added.

== Give the pod its SPIFFE identity

Three edits in `globex-complaint-agent-helm`, in this order.

=== The helper configuration

Create `templates/configmap.yaml`:

[source,yaml,role="copypaste"]
----
kind: ConfigMap
apiVersion: v1
metadata:
  name: spiffe-workload-agent-spiffe-helper
data:
  helper.conf: |-
    agent_address = "/spiffe-workload-agent/spire-agent.sock"
    cmd = ""
    cmd_args = ""
    cert_dir = "/svids"
    renew_signal = ""
    svid_file_name = "svid.pem"
    svid_key_file_name = "svid_key.pem"
    svid_bundle_file_name = "svid_bundle.pem"
    jwt_svids = [{jwt_audience="{{ .Values.oidc.internal.authServerUrl }}/realms/{{ .Values.oidc.internal.realm }}", jwt_svid_file_name="jwt.token"}]
    jwt_bundle_file_name  = "jwt_bundle.json"
----

`jwt_audience` is the Keycloak realm URL. SPIRE mints the SVID *for* that audience, and Keycloak rejects one minted for anything else.

=== The pod

In `templates/deployment.yaml`, add the init container and the sidecar above the existing application container:

[source,yaml,role="copypaste"]
----
      initContainers:
        - name: init-spiffe-helper
          image: {{ .Values.spiffeHelper.image }}
          imagePullPolicy: IfNotPresent
          args:
            - '-config'
            - /etc/helper.conf
            - '-daemon-mode=false'
          volumeMounts:
            - name: spiffe-helper-config
              readOnly: true
              mountPath: /etc/helper.conf
              subPath: helper.conf
            - name: spiffe-workload-agent
              readOnly: true
              mountPath: /spiffe-workload-agent
            - name: svids
              mountPath: /svids
----

              readOnly: true
              mountPath: /spiffe-workload-agent
            - name: svids
              mountPath: /svids
----

Same image and same configuration twice. `-daemon-mode=false` is the whole difference: the init container fetches one SVID and exits, the sidecar stays and renews.

Give the application container the token by adding to its `volumeMounts`:

[source,yaml,role="copypaste"]
----
            - name: svids
              mountPath: /svids
----

And add the three volumes:

[source,yaml,role="copypaste"]
----
        - name: spiffe-helper-config
          configMap:
            name: spiffe-workload-agent-spiffe-helper
            defaultMode: 420
        - name: svids
          emptyDir: {}
        - name: spiffe-workload-agent
          csi:
            driver: csi.spiffe.io
            readOnly: true
----

[NOTE]
====
`csi.spiffe.io` is the interesting one. It carries no data -- it mounts the node's SPIRE agent socket into the pod. The SPIRE agent on the other end of that socket identifies the caller from the kernel, by process, and cross-checks it with the kubelet. That is why the pod needs nothing to prove who it is: it cannot lie about which pod it is.
====

== Swap the secret for the SVID

In `values.yaml`, add the SPIFFE block:

[source,yaml,role="copypaste"]
----
spiffe:
  trustDomain: globex.com
  namespace: globex-complaint-agent
  serviceAccount: globex-complaint-agent
  clientId: globex-agent-spiffe
  oidcIssuer: spiffe
  tokenPath: /svids/jwt.token

spiffeHelper:
  image: registry.redhat.io/zero-trust-workload-identity-manager/spiffe-helper-rhel9:v0.10.0
----

Then in `templates/secret.yaml`, *delete* the two `credentials.secret` lines you added on the last page and put these in their place:

[source,yaml,role="copypaste"]
----
    quarkus.oidc-client.orders.client-id={{ .Values.spiffe.clientId }}
    quarkus.oidc-client.orders.credentials.jwt.token-path={{ .Values.spiffe.tokenPath }}
    quarkus.oidc-client.orders.credentials.jwt.source=bearer
    quarkus.oidc-client.orders.credentials.jwt.issuer={{ .Values.spiffe.oidcIssuer }}
    quarkus.oidc-client.orders.credentials.jwt.subject=spiffe://{{ .Values.spiffe.trustDomain }}/ns/{{ .Values.spiffe.namespace }}/sa/{{ .Values.spiffe.serviceAccount }}

    quarkus.oidc-client.complaint.client-id={{ .Values.spiffe.clientId }}
    quarkus.oidc-client.complaint.credentials.jwt.token-path={{ .Values.spiffe.tokenPath }}
    quarkus.oidc-client.complaint.credentials.jwt.source=bearer
    quarkus.oidc-client.complaint.credentials.jwt.issuer={{ .Values.spiffe.oidcIssuer }}
    quarkus.oidc-client.complaint.credentials.jwt.subject=spiffe://{{ .Values.spiffe.trustDomain }}/ns/{{ .Values.spiffe.namespace }}/sa/{{ .Values.spiffe.serviceAccount }}
----

`source=bearer` is what tells Quarkus the JWT is already signed and is to be sent as-is. Without it, Quarkus would try to mint and sign its own assertion -- which is the normal RFC 7523 flow, and exactly what you do not want here. The subject is the SPIFFE ID the SVID carries, and it has to match the `jwt.credential.sub` recorded on the Keycloak client.

Also remove the `oidcClient.*.secret` entries from `values.yaml`. Nothing reads them now, and leaving a live secret in Git after a page about removing it defeats the exercise.

Commit each file to `main`.

== Watch the rollout

The pod now has three containers, and the order they come up in is the thing to watch: `init-spiffe-helper` must complete before anything else starts. If it hangs, the CSI volume is not mounting and no SVID is being issued -- the agent container never starts at all.
