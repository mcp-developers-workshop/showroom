= Require a Token on the Orders MCP Server
:numbered:
:icons: font
:source-highlighter: highlight.js

[IMPORTANT]
====
Everything on this page happens in the *`globex-store-mcp`* folder -- the MCP server you built in Module 1, not the agent.
====

== Add the OIDC extension

From inside `globex-store-mcp`:

[source,sh,role="copypaste"]
----
./mvnw quarkus:add-extension -Dextensions="oidc"
----

[NOTE]
====
`quarkus-oidc` and `quarkus-oidc-client` are two different extensions and the names are one word apart.

* `quarkus-oidc` makes an application a *resource server*: it validates tokens that arrive. That is what you want here.
* `quarkus-oidc-client` makes an application a *client*: it fetches tokens to send. The agent gets that one later.
====

== Configure it

Add to `src/main/resources/application.properties`:

[source,properties,role="copypaste",subs="attributes+"]
----
# OIDC - validate access tokens from the internal realm
quarkus.oidc.auth-server-url=https://sso.{openshift_subdomain}/realms/internal
quarkus.oidc.client-id=globex-mcp-server
quarkus.oidc.token.audience=globex-mcp-server

# Secure the MCP endpoint
quarkus.http.auth.permission.mcp.paths=/mcp,/mcp/*
quarkus.http.auth.permission.mcp.policy=authenticated
----

Three things are happening:

`auth-server-url` points at the `internal` realm. That is a different realm from the one the chatbot signs users into. Customers live in `globex`; workloads live in `internal`.

`token.audience` narrows what the server accepts. Without it the server accepts any valid token the realm issued, for any purpose -- including one minted for a completely different service. With it, the token has to carry `aud: globex-mcp-server`, which means it was issued *to be used here*.

`http.auth.permission.mcp` applies the policy. Anything under `/mcp` now needs an authenticated caller.

[NOTE]
====
The `internal` realm and every client this module names are created when your lab environment is provisioned. `globex-mcp-server` above already exists, as do the complaints server client on the next page and the agent's two clients on page 5. You create nothing in Keycloak in this module -- the configuration you write refers to clients that are already there.
====

[NOTE]
====
No client secret appears anywhere on this page. The server only *validates* tokens, and it does that with the realm's public keys, which it downloads from `auth-server-url` when it starts. A resource server needs no credentials of its own. The agent is the one that has to prove who it is, and that is where secrets show up.
====
