Two-step arc: earn identity with OIDC client credentials first, then replace the shared
secret with SPIFFE workload identity. Step 1 is the mechanism most teams already have;
Step 2 is what it does not solve.

*Module 3 runs against the cluster, not localhost.* Module 2 ends with the chatbot
pointed at the deployed agent route, and Module 3 continues from there: edit, push, let
the pipeline build, watch it on OpenShift. Nothing runs in dev mode. The identity
configuration is cluster-side anyway -- Keycloak realms, service accounts, audience
mappers -- and testing locally would mean putting the client secret on the attendee's
laptop and maintaining a second config path.

Consequences to carry through every page:

* *Compile locally, test on the cluster.* Attendees hand-write a class in section 04. Tell
  them to run `mvn clean compile` before pushing, or a typo costs a full pipeline
  round-trip to discover.
* *Push the two servers together.* Sections 02 and 02b both end in a push; if the
  attendee pushes both and then watches, the pipelines run concurrently and there is one
  wait instead of two.
* *Say up front that there is no live reload.* Module 2 gave instant feedback from
  `quarkus:dev`. Module 3 does not, and an attendee who does not know that will assume
  their change failed.

== Step 1 -- OIDC and Keycloak

=== 01 Baseline: the server trusts anyone

The orders MCP server has no authentication. Anything that can reach the route can call
any tool and claim to be any customer via `X-User-Id`. Module 1 and Module 2 both flag
this inline; this page is where it gets demonstrated rather than asserted.

* Call the deployed tool from the MCP Inspector with no credentials -- it works.
* Set `X-User-Id` to a different customer -- their orders come back.

=== 02 Require a token on the MCP server

Everything in this section happens in the *`globex-store-mcp`* folder -- the MCP server.

Add the extension:

[source,sh,role="copypaste"]
----
./mvnw quarkus:add-extension -Dextensions="oidc"
----

[NOTE]
====
`oidc`, not `oidc-client`. `quarkus-oidc` makes an application a *resource server*: it
validates tokens that arrive. `quarkus-oidc-client` does the opposite -- it *fetches*
tokens to send somewhere else, and that one goes on the agent in section 04. Adding the
wrong one leaves `policy=authenticated` below with no authentication mechanism behind it.
====

Then `src/main/resources/application.properties`, still in `globex-store-mcp`:

[source,properties,subs="attributes+"]
----
# OIDC Configuration for Service Account Authentication
quarkus.oidc.auth-server-url=https://sso.{openshift_subdomain}/realms/internal
quarkus.oidc.client-id=globex-mcp-server
quarkus.oidc.token.audience=globex-mcp-server

# Secure MCP endpoints
quarkus.http.auth.permission.mcp.paths=/mcp,/mcp/*
quarkus.http.auth.permission.mcp.policy=authenticated
----

* `internal` realm, not `globex` -- `globex` is the customer realm the chatbot uses.
* These properties ride to the cluster in the image, not through a chart -- unlike the
  agent in Module 2, `globex-store-mcp` has no attendee-editable Helm repository. That
  works because a resource server only validates tokens and holds no secret.
* Audience validation is the part that matters: a token minted for something else is
  rejected, not merely any valid token accepted.

Check it compiles before pushing -- there is no dev mode to catch mistakes here:

[source,sh,role="copypaste"]
----
./mvnw clean compile
----

Then commit and push, exactly as in Module 1:

[source,sh,role="copypaste"]
----
git add .
git commit -m "require a token on the MCP server"
git push
----

The push triggers the `globex-store-mcp-build` pipeline, which builds a new image and
rolls it out. Do not wait for it yet -- push the complaints server first and let both
builds run together.

==== Secure both endpoints

Add to `src/main/resources/application.properties`:

[source,properties,subs="attributes+"]
----
# OIDC Configuration for Service Account Authentication
quarkus.oidc.auth-server-url=https://sso.{openshift_subdomain}/realms/internal
quarkus.oidc.client-id=globex-complaints-server

# Secure both MCP endpoints
quarkus.http.auth.permission.mcp.paths=/mcp,/mcp/*,/read/mcp,/read/mcp/*

[NOTE]
====
No client secret here. The complaints server only *validates* tokens, and it does that
with the realm's public keys, which it fetches from `auth-server-url` at startup. A
resource server needs no credentials of its own. The agent, in section 04, is the one
that has to prove who it is -- that is where secrets appear.

=== 04 Give the agent a service account

[IMPORTANT]

The agent needs an identity of its own. Add the extension:

[source,sh,role="copypaste"]
----
mvn quarkus:add-extension -Dextensions="oidc-client"
----

`quarkus-oidc` is already on the agent -- it is how the agent validates the user's JWT.
That is the *resource server* side. What is new here is the *client* side: getting a token
of the agent's own.

The agent talks to two MCP servers, so it needs two OIDC clients -- one per server, each
named after the MCP client it serves. The URLs and client IDs are not secret, so they go
in `src/main/resources/application.properties`:

[source,properties,subs="attributes+"]
----
quarkus.oidc-client.orders.auth-server-url=https://sso.{openshift_subdomain}/realms/internal
quarkus.oidc-client.orders.client-id=globex-mcp-client

quarkus.oidc-client.complaint.auth-server-url=https://sso.{openshift_subdomain}/realms/internal
quarkus.oidc-client.complaint.client-id=globex-agent-complaints-client
----

`orders` and `complaint` are the names the MCP clients already use --
`quarkus.langchain4j.mcp.orders.*` and `quarkus.langchain4j.mcp.complaint.*` from Module 2.
Reusing them for the OIDC clients is a convention, not a requirement, and it is what keeps
the next two classes readable.

The client secrets do *not* go here -- `application.properties` is baked into the
container image. They travel the same route the model API key took in Module 2: the
Secret template and `values.yaml` in `globex-complaint-agent-helm`.

[NOTE]

`values.yaml` is committed to Git, so the secret is committed with it -- the same
shortcut the model API key took in Module 2. In production the secret would come from a
secret manager, rotate on a schedule, and never reach the repository. The workshop keeps

`GlobexMcpAuthProvider.java`:

[source,java,role="copypaste"]
----
package org.globex.retail.ai.complaint.auth;

import io.quarkiverse.langchain4j.mcp.auth.McpClientAuthProvider;
import io.quarkiverse.langchain4j.mcp.runtime.McpClientName;
import io.quarkus.oidc.client.NamedOidcClient;
import io.quarkus.oidc.client.OidcClient;
import io.quarkus.oidc.client.runtime.TokensHelper;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
@McpClientName("orders")
public class GlobexMcpAuthProvider implements McpClientAuthProvider {

    @Inject
    @NamedOidcClient("orders")
    OidcClient globexStoreClient;

    TokensHelper tokens = new TokensHelper();

    @Override
    public String getAuthorization(Input input) {
        return "Bearer " + tokens.getTokens(globexStoreClient).await().indefinitely().getAccessToken();
    }
}
----

Two names in that class, and they refer to different things even though they read the same:

* `@McpClientName("orders")` is the *MCP client* -- the one configured by
  `quarkus.langchain4j.mcp.orders.*` and named in `@McpToolBox("orders")`. It tells
  Quarkus which MCP client this provider supplies the header for.
* `@NamedOidcClient("orders")` is the *OIDC client* -- the one configured by
  `quarkus.oidc-client.orders.*`. It is where the token comes from.

`TokensHelper` caches the token and refreshes it when it expires, so Keycloak is not
called on every tool invocation.

package org.globex.retail.ai.complaint.auth;

import io.quarkiverse.langchain4j.mcp.auth.McpClientAuthProvider;
import io.quarkiverse.langchain4j.mcp.runtime.McpClientName;
import io.quarkus.oidc.client.NamedOidcClient;
import io.quarkus.oidc.client.OidcClient;
import io.quarkus.oidc.client.runtime.TokensHelper;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
@McpClientName("complaint")
public class GlobexComplaintMcpAuthProvider implements McpClientAuthProvider {

    @Inject
    @NamedOidcClient("complaint")
    OidcClient complaintClient;

    TokensHelper tokens = new TokensHelper();

    @Override
    public String getAuthorization(Input input) {
        return "Bearer " + tokens.getTokens(complaintClient).await().indefinitely().getAccessToken();
    }
}
----

Identical but for the two names. That is the rule this page exists to make concrete: one
provider per MCP client, each wired to its own OIDC client, each presenting a different
identity. A third MCP server would need a third.

These sit alongside `GlobexMcpHeadersSupplier` from Module 2. All three are active: the
providers supply `Authorization`, the supplier supplies `X-User-Id`.

=== 05 Two tokens, two realms

Nothing in Modules 1 and 2 changes. `X-User-Id` stays exactly as it is; the service-account
token is added alongside it.

....
globex-web  --user JWT (globex realm)-->  agent  --SA token (internal realm)-->  MCP server
                                                 --X-User-Id: asilva----------->
....

`globex-web` signs the user in against Keycloak and posts the user's JWT to the agent on
the same endpoint the chatbot uses. The agent validates it, takes `preferred_username`
from it -- `AuthoritativeUserIdHolder`, unchanged from Module 2 -- and sends that as
`X-User-Id`. It authenticates to the MCP server as itself.

The user's token is never forwarded, and could not be: it is issued by the `globex` realm
for a different audience, so `globex-mcp-server` would reject it. The MCP specification
forbids this passthrough for the same reason.

What this does and does not fix, stated plainly on the page:

* *Fixed* -- the route is no longer open. An unauthenticated caller gets 401, and a token
  minted for something else fails the audience check.
* *Not fixed* -- the MCP server still believes the agent about which customer is asking.
  The agent is trusted rather than verified.

The `[IMPORTANT]` note at the end of `m2/05-pass-user-id.adoc` says this gets fixed later
in the workshop. It is narrowed here, not closed -- so either that note or this page has
to be honest about which.

== Step 2 -- SPIFFE workload identity

=== 06 Why the client secret is not enough

`globex-mcp-client`'s secret is a long-lived bearer credential. Module 2 already committed
one to Git in `values.yaml`, which makes the point concrete. Anything holding it is the
agent, forever, from anywhere. Nothing attests that the caller is the workload it claims
to be, nothing binds the credential to where it runs, and rotation is manual.

SPIFFE replaces the shared secret with an identity the platform attests and short-lived
credentials nobody has to store.

=== 07 SPIRE sidecar on the agent

* Introduce the SPIFFE sidecar alongside the agent.
* Agent obtains a JWT-SVID from the workload API instead of using a client secret.

=== 08 Keycloak configuration

* Federate the SPIFFE trust domain / accept the JWT-SVID as a client assertion.
* Map the SPIFFE ID to the existing service account.

== Settled

* *Client credentials, not token exchange.* The agent authenticates to the MCP server as
  itself, with its own service-account token from the `internal` realm.
* *`X-User-Id` stays.* The user identity keeps travelling in the header, exactly as built
  in Module 2. Modules 1 and 2 need no code changes, and their sign-off holds.
* *Both MCP servers get secured, and attendees clone `globex-complaints`.* Securing only
  orders makes the failure non-deterministic -- which server the agent calls first is the
  model's choice for that prompt, not a fixed order -- so some attendees would see the
  401 on the "watch it break" page and others would not. It also leaves half the attack
  surface open in a security module. Feasible with no new machinery: the org has
  `mcp-developers-workshop/globex-complaints` and `install-helm/globex-complaints-build`
  is the same GitLab-webhook / buildah / ArgoCD-resync loop used for the agent in
  Module 2. The POC did exactly this, with one Keycloak client per server
  (`globex-mcp-client` for orders, `globex-agent-complaints-client` for complaints, both
  in `internal`) and one `McpClientAuthProvider` per MCP client. The repetition earns its
  place: it is what teaches that a provider is per-client, not per-application.

* *Attendees clone three repositories in Module 3, and no chart for the complaints
  server.* Decided 2026-10-01. The ideal is that every piece of deployment configuration
  an attendee changes lives in the workshop GitLab and is edited there, the way
  `globex-complaint-agent-helm` is. For the complaints server that would mean a fourth
  clone and a second place to edit, to carry configuration that is not secret. Not worth
  it. So the complaints server is configured in its own `application.properties`, in the
  repository attendees already clone in 02b, and its chart stays in the install
  repository where attendees never see it.
+
This costs nothing, because the complaints server holds no secret: it is a resource
server, and it validates tokens with the realm's public keys fetched from
`auth-server-url`. The only environment-specific value committed is that URL, which is
public. The agent is the one case where a real secret has to travel, and it already has
`globex-complaint-agent-helm` cloned from Module 2 -- so the Helm route is used exactly
where it earns its keep and nowhere else.
+
Repository count for Module 3: `globex-store-mcp` and `globex-complaint-agent` and
`globex-complaint-agent-helm` are already cloned from Modules 1 and 2; `globex-complaints`
is the one new clone.

* *No sidecar in Step 1.* Step 1 is plain OIDC -- an extension and configuration, nothing
  added to the pod. The SPIRE sidecar arrives with SPIFFE in Step 2, which makes the
  before/after obvious: the shared secret goes away and something appears next to the
  agent to replace it. Both "no sidecar" claims are now out of `m3/index.adoc`, but the
  rest of that page is still the original outline and needs a full rewrite once the lab
  is walked -- wrong agenda filenames, a `globex-agent` repo that does not exist, and
  guardrails it may not cover.
