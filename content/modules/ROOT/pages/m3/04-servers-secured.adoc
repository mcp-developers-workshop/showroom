Both servers now ask for a token. Nothing about the agent has changed -- it is the same image you deployed at the end of Module 2, calling the same two URLs, and it has never had a token to send.

== Run the handshake again

This is the same command from the first page of this module, unchanged:

[source,sh,role="copypaste",subs="attributes+"]
----
curl -i -X POST https://globex-store-mcp.{openshift_subdomain}/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}'
----

[source,text]
----
HTTP/1.1 401 Unauthorized
www-authenticate: Bearer
----

And the complaints server:

[source,sh,role="copypaste",subs="attributes+"]
----
curl -i -X POST https://globex-complaints.{openshift_subdomain}/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}'
----

Both routes are closed to `curl` call and therefore to the agent as well.

====
You may also find the agent itself unhealthy in ArgoCD. An MCP client asks its server for the tool list when it starts, long before anyone chats to it, so the agent has been failing against these servers since the moment they rolled out.
