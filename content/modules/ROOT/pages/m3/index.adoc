= Module 3: Enable Security & Identity (Zero-Trust)
:numbered:
:icons: font
:source-highlighter: highlight.js

== Overview & Objectives
The MCP servers you built and used in Modules 1 and 2 are on public routes and will answer anyone who can reach them. This module closes them. The agent gets a Keycloak identity of its own, proves it with the client credentials grant, and presents the resulting token on every MCP call -- while the signed-in customer's identity keeps travelling separately, in the header you built in Module 2.

That is Step 1, and it is what this module currently covers end to end. Step 2 replaces the agent's shared secret with a SPIFFE workload identity that the platform attests; it is outlined here and still being written.

=== Learning Objectives
* Understand the security hazards of direct, unauthenticated agentic access.
* Tell a resource server from a client, and know why only one of them needs a secret.
* Secure a Quarkus MCP endpoint with OIDC, including the audience check that makes a token specific to the service it was issued for.
* Obtain a token with the client credentials grant and attach it to MCP calls with an `McpClientAuthProvider`.
* Keep workload identity and user identity separate, and know why the MCP specification forbids forwarding a user's token downstream.

== Architecture & Components
* *Identity Provider:* Keycloak -- the `globex` realm for customers, the `internal` realm for workloads
* *MCP Servers:* Quarkus Orders and Complaints MCP servers, with `quarkus-oidc` and an authenticated permission policy
* *AI Agent:* Globex Complaints & Order Assistant, with `quarkus-oidc-client` and one auth provider per MCP client
* *Security Mechanisms:* OAuth2 client credentials grant, JWT validation against realm public keys, audience restriction
* *Deployment Pipeline:* GitLab, OpenShift build, ArgoCD sync -- as in Module 2

== Prerequisites
* Modules 1 and 2 completed, with the agent and both MCP servers deployed and working
* The chatbot pointed at the deployed agent route, as left at the end of Module 2
* Keycloak `internal` realm, pre-seeded with the workload clients this module uses

[IMPORTANT]
====
This module runs against the cluster. You edit code locally, push, and let the pipeline build and roll out -- there is no dev mode and no live reload here, unlike Module 2. Compile before every push.
====

== Lab Agenda
1. Call both MCP servers with no credentials and confirm they answer
2. Require an authenticated caller on the orders MCP server
3. Require an authenticated caller on both endpoints of the complaints MCP server
4. Confirm both servers now reject anonymous callers, and that the unchanged agent is one of them
5. Give the agent its own Keycloak client credentials and attach the resulting tokens to MCP calls
6. Separate workload identity from user identity, and name what is still unfixed
7. Replace the shared secret with a SPIFFE workload identity -- outline only, still being written

== Expected Outcomes
Two MCP servers that reject anonymous callers, and an agent that reaches them as an authenticated workload with a token scoped to each server -- while the customer's identity continues to travel in a header the server has not yet verified.
