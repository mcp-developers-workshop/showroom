= Two Tokens, Two Realms
:numbered:
:icons: font
:source-highlighter: highlight.js

Nothing from Modules 1 and 2 was taken away to get here. `X-User-Id` still carries the customer, exactly as you built it. The agent's own token was added alongside it.

....
chatbot  --user JWT (globex realm)-->  agent  --SA token (internal realm)-->  MCP server
                                              --X-User-Id: asilva----------->
....

Two tokens, from two realms, answering two different questions:

[cols="1,1,1", options="header"]
|===
| | User JWT | Agent token

| Realm
| `globex`
| `internal`

| Who it describes
| The signed-in customer
| The agent workload

| Who issues it to whom
| Keycloak, to the chatbot, after the customer signs in
| Keycloak, to the agent, on a client ID and secret

| Where it stops
| The agent validates it and does not pass it on
| The MCP servers validate it
|===

The agent validates the user's JWT, takes `preferred_username` from it -- `AuthoritativeUserIdHolder`, unchanged from Module 2 -- and sends that value as `X-User-Id`. Then it authenticates to the MCP server as itself.

== Why the user's token is not forwarded

It would be the obvious shortcut, and it is wrong twice over.

It would not work: the user's token is issued by the `globex` realm for a different audience, so `globex-mcp-server` would reject it.

And it is specifically forbidden. The MCP specification rules out passing a client's token straight through to a downstream server. A token is issued for a particular audience; forwarding it means some other service can now replay it, and the audience check that makes `token.audience` worth setting stops meaning anything.

== What this fixed, and what it did not

*Fixed.* The routes are no longer open. An anonymous caller gets 401, and a token minted for something else fails the audience check. Every call to an MCP server now comes from a workload that proved its identity to Keycloak.

*Not fixed.* The MCP server still believes the agent about which customer is asking. `X-User-Id` is still an unverified claim -- the difference is that only an authenticated workload can make it. The agent is trusted rather than verified.
