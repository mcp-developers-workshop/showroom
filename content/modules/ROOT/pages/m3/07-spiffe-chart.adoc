= SPIFFE Step 1: Move the Chart to the SVID
:numbered:
:icons: font
:source-highlighter: highlight.js

[IMPORTANT]
====
This page works in the *`globex-complaint-agent-helm`* repository. Four files, and they belong in *one commit*.
====

Everything the agent needs to stop using its client secret is in this one chart, and the four files only work together:

[cols="1,2", options="header"]
|===
| File | What it does

| `values.yaml`
| The helper image, and the SPIFFE identity the chart is built around.

| `templates/configmap.yaml`
| New. Tells `spiffe-helper` which socket to use, where to write, and what audience to ask for.

| `templates/deployment.yaml`
| Adds an init container, a sidecar, a shared volume and the mount that puts the token where the application can read it.

| `templates/secret.yaml`
| Points both OIDC clients at the token file instead of at a secret.
|===

== Edit the chart

In the `globex-complaint-agent-helm` window, pull first:

[source,sh,role="copypaste"]
----
git pull

=== `values.yaml`

Two blocks to add and two entries to delete. This file holds your OpenAI API key and your cluster URLs, so edit it rather than replacing it.

Add at the end:

[source,yaml,role="copypaste"]
----
spiffeHelper:
  image: registry.redhat.io/zero-trust-workload-identity-manager/spiffe-helper-rhel9:v0.10.0

spiffe:
  trustDomain: globex.com
  namespace: globex-complaint-agent
  serviceAccount: globex-complaint-agent
  clientId: globex-agent-spiffe
  tokenPath: /svids/jwt.token
----

Then cut the `oidcClient` block down to the two URLs. Nothing reads the client IDs or the secrets once `secret.yaml` below is in place, and leaving a live secret in Git after a page about removing it defeats the exercise:

[source,yaml,role="copypaste",subs="attributes+"]
----
oidcClient:
  orders:
    authServerUrl: https://sso.{openshift_subdomain}/realms/internal
  complaint:
    authServerUrl: https://sso.{openshift_subdomain}/realms/internal
----

[WARNING]
====
Keep both `authServerUrl` entries. `configmap.yaml` below reads `oidcClient.orders.authServerUrl` to decide which audience SPIRE mints the SVID for, so deleting the whole block -- the tidy-looking thing to do, since almost everything in it is now dead -- produces an SVID that Keycloak rejects, two pages after the edit that caused it.
====

=== `templates/configmap.yaml`

New file:

[source,yaml,role="copypaste"]
----
kind: ConfigMap
apiVersion: v1
metadata:
  name: spiffe-workload-agent-spiffe-helper
data:
  helper.conf: |-
    agent_address = "/spiffe-workload-agent/spire-agent.sock"
    cmd = ""
    cmd_args = ""
    cert_dir = "/svids"
    renew_signal = ""
    svid_file_name = "svid.pem"
    svid_key_file_name = "svid_key.pem"
    svid_bundle_file_name = "svid_bundle.pem"
    jwt_svids = [{jwt_audience="{{ .Values.oidcClient.orders.authServerUrl }}", jwt_svid_file_name="jwt.token"}]
    jwt_bundle_file_name  = "jwt_bundle.json"
----

`jwt_audience` is the Keycloak realm URL. SPIRE mints the SVID *for* that audience and Keycloak rejects one minted for anything else. Both OIDC clients point at the same realm, so either key gives the same value.

=== `templates/deployment.yaml`

The file describes a single-container pod today. It gains four things:

* An *init container*, `init-spiffe-helper`, which fetches the first SVID and exits before the agent starts.
* A *sidecar*, `spiffe-helper`, which renews it for the life of the pod. Same image and same configuration -- `-daemon-mode=false` is the only difference between them. Neither needs a `securityContext`; the pod-level one already in the file applies to all three containers.
* A `svids` *mount on the application container*, next to the `/deployments/config` mount it already has. This is the one that matters: everything else here exists to put a current token at `/svids/jwt.token` for the application to read.
* Three more *volumes*: `spiffe-helper-config` for the ConfigMap, `svids` as the scratch directory all three containers share, and `spiffe-workload-agent` for the socket.

That is four edits scattered through a YAML file where indentation decides whether it parses. Select all and replace:

[NOTE]
====
`csi.spiffe.io` carries no data. It mounts the node's SPIRE agent socket into the pod. The SPIRE agent on the other end identifies the caller from the kernel, by process, and cross-checks it with the kubelet, so the pod supplies no credential and cannot misreport which pod it is.

The SPIFFE ID it is issued is built from the pod's namespace and service account, and the Keycloak client is pinned to that exact string. Leave `serviceAccountName` alone.
====

== What you just configured

`source=spiffe-jwt` does two things. It tells Quarkus the JWT at `token-path` is already signed and is to be sent as-is -- the default, `client`, has Quarkus mint and sign its own assertion, which is the normal RFC 7523 flow but would discard the SVID. And it sets `client_assertion_type` to `urn:ietf:params:oauth:client-assertion-type:jwt-spiffe`, which is what Keycloak's SPIFFE support expects. RFC 7523's own value, `...:jwt-bearer`, is what you would get from `source=bearer`, and Keycloak rejects it here.

[NOTE]
====
With `spiffe-jwt`, Quarkus checks the token's `sub` claim starts with `spiffe://` *before* sending anything, and fails with `SPIFFE JWT-SVID token 'sub' claim is missing or does not start with 'spiffe://'`. A bad or truncated token file gives you that in the agent log, rather than an opaque `invalid_client` from Keycloak.
====

Both OIDC clients now send the same `client-id`. That is the shift this page makes: the agent had two Keycloak identities, one per downstream server, each with its own secret. It has one identity now -- itself -- and proves it the same way to both.

[NOTE]
====
One identity does not mean one audience, but on this cluster it nearly does. `globex-agent-spiffe` carries a protocol mapper that puts `globex-mcp-server` in the audience of every token it is issued, so both MCP servers now see the same `aud`. The orders server checks it and is satisfied; the complaints server does not check at all, so it accepts a token minted for its neighbour.

That is not a regression -- the complaints client never had an audience of its own to lose, which is why that server has no audience check in the first place.
====

[WARNING]
====
No trailing spaces at the ends of the property lines. The block is a YAML literal scalar, so a space after `}}` ends up inside the value.
====

== Check it before you move on

In the https://console-openshift-console.{openshift_subdomain}/k8s/ns/globex-complaint-agent/secrets[OpenShift console^], open the `globex-complaint-agent` secret and reveal `application.properties`. Three things:

* No property has an *empty* value. Read the right-hand side of every `quarkus.oidc-client.*` line.
* `quarkus.oidc-client.orders.client-id` and `...complaint.client-id` both read `globex-agent-spiffe`.
* There is no `credentials.secret` anywhere in the file.

Then check the pod is *2/2* with `init-spiffe-helper` completed.

[IMPORTANT]
====
*ArgoCD showing `Synced` does not mean the values resolved.* It means the chart rendered and the result was applied. A template that reads a key you have deleted from `values.yaml` renders an empty string, not an error -- `oidcClient.complaint` still exists as a map, so `.clientId` on it is simply blank. The Secret applies, ArgoCD goes green, and the agent is configured with no client ID.
====

[NOTE]
====
If the pod sits at *1/2* with the application container running but never ready, open its log. A repeating health check like this is the symptom:

....
"status":"DOWN","checks":[{"name":"MCP clients health check","status":"DOWN",
 "data":{"complaint":"...DisabledOidcClientException: 'complaint' client
 configuration is not initialized","orders":"..."}}]
....

That message is the same for every cause -- a missing `auth-server-url`, a missing `client-id`, a `token-path` that is not set when `jwt.source` is. Quarkus logs the real reason at DEBUG and shows you only this. Go back to the Secret and look for the empty value; do not go looking at SPIRE or Keycloak, because neither has been reached yet.

The pod stays at *1/2* rather than crash-looping, and the previous pod keeps serving traffic, so the storefront still works. Nothing looks broken until the next page.
====
