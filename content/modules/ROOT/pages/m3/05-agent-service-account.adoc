= Authenticate the Agent to the MCP Servers
:numbered:
:icons: font
:source-highlighter: highlight.js

[IMPORTANT]
====
This page switches projects. Everything here happens in the *`globex-complaint-agent`* folder -- the agent, not either MCP server. Open a terminal there before continuing.
====

== Add the OIDC client extension

[source,sh,role="copypaste"]
----
mvn quarkus:add-extension -Dextensions="oidc-client"
----

`quarkus-oidc` is already on the agent, validating the user's JWT from the chatbot. That is the resource server side. What is new here is the client side: getting a token of the agent's own.

[WARNING]
====
`quarkus.oidc.*` and `quarkus.oidc-client.*` are different configuration trees and they are one character apart.

* `quarkus.oidc.*` -- already configured, do not touch it. The agent *validating* incoming user tokens against the `globex` realm.
* `quarkus.oidc-client.*` -- what you add below. The agent *fetching* its own token from the `internal` realm.

Two realms, two opposite directions.
====

== Configure two OIDC clients

The agent talks to two MCP servers, and it has a separate Keycloak identity for each. The URLs and client IDs are not secret, so they go in `src/main/resources/application.properties`:

[source,properties,role="copypaste",subs="attributes+"]
----
quarkus.oidc-client.orders.auth-server-url=https://sso.{openshift_subdomain}/realms/internal
quarkus.oidc-client.orders.client-id=globex-mcp-client

quarkus.oidc-client.complaint.auth-server-url=https://sso.{openshift_subdomain}/realms/internal
quarkus.oidc-client.complaint.client-id=globex-agent-complaints-client
----

`orders` and `complaint` are the MCP client names from `quarkus.langchain4j.mcp.orders.*` and `quarkus.langchain4j.mcp.complaint.*` in Module 2. Use them verbatim: the next two classes bind each MCP client to its OIDC client by name, and a mismatch binds nothing.

This is the *client credentials* grant: the agent presents a client ID and secret to Keycloak and gets back an access token that says it is that client. No user is involved -- this token answers "which workload is calling", not "who is the customer".

[WARNING]
====
The client secrets do not go in `application.properties`. That file is committed to Git and baked into the container image. They go in the Helm chart, further down this page.
====

== Write the auth providers

An MCP client asks an `McpClientAuthProvider` for the `Authorization` header on every call. `@McpClientName` ties one provider to one MCP client, so two MCP clients need two providers -- there is no way to write a single class that covers both.

These go in the same `auth` package as `GlobexMcpHeadersSupplier` from Module 2:

[source,sh,role="copypaste"]
----
mkdir -p src/main/java/org/globex/retail/ai/complaint/auth
touch src/main/java/org/globex/retail/ai/complaint/auth/GlobexMcpAuthProvider.java
touch src/main/java/org/globex/retail/ai/complaint/auth/GlobexComplaintMcpAuthProvider.java
----

[IMPORTANT]
====
Check two things before you paste, or the editor will fill both files with errors:

* *You are in `globex-complaint-agent`.* `McpClientName` and `McpClientAuthProvider` come from `quarkus-langchain4j-mcp`, which is the MCP *client* library. Neither MCP server has that dependency, so in those projects these types do not exist at all.
* *The extension is added and the project has reloaded.* Create the classes before `quarkus-oidc-client` is on the classpath and the editor reports every import as unresolved -- including the ones that were already available -- because the file as a whole fails to resolve.
====

Open `GlobexMcpAuthProvider.java` and paste:

[source,java,role="copypaste"]
----
package org.globex.retail.ai.complaint.auth;

import io.quarkiverse.langchain4j.mcp.auth.McpClientAuthProvider;
import io.quarkiverse.langchain4j.mcp.runtime.McpClientName;
import io.quarkus.oidc.client.NamedOidcClient;
import io.quarkus.oidc.client.OidcClient;
import io.quarkus.oidc.client.runtime.TokensHelper;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
@McpClientName("orders")
public class GlobexMcpAuthProvider implements McpClientAuthProvider {

    @Inject
    @NamedOidcClient("orders")
    OidcClient globexStoreClient;

    TokensHelper tokens = new TokensHelper();

    @Override
    public String getAuthorization(Input input) {
        return "Bearer " + tokens.getTokens(globexStoreClient).await().indefinitely().getAccessToken();
    }
}
----

Two annotations carry the name `orders`, and they refer to different things:

* `@McpClientName("orders")` is the *MCP client* -- the one configured by `quarkus.langchain4j.mcp.orders.*` and named in `@McpToolBox("orders")`. It tells Quarkus which client this provider supplies the header for.
* `@NamedOidcClient("orders")` is the *OIDC client* -- the one you configured above as `quarkus.oidc-client.orders.*`. It is where the token comes from.

`TokensHelper` caches the token and refreshes it when it expires, so Keycloak is not called on every tool invocation.

Now `GlobexComplaintMcpAuthProvider.java`:

[source,java,role="copypaste"]
----
package org.globex.retail.ai.complaint.auth;

import io.quarkiverse.langchain4j.mcp.auth.McpClientAuthProvider;
import io.quarkiverse.langchain4j.mcp.runtime.McpClientName;
import io.quarkus.oidc.client.NamedOidcClient;
import io.quarkus.oidc.client.OidcClient;
import io.quarkus.oidc.client.runtime.TokensHelper;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
@McpClientName("complaint")
public class GlobexComplaintMcpAuthProvider implements McpClientAuthProvider {

    @Inject
    @NamedOidcClient("complaint")
    OidcClient complaintClient;

    TokensHelper tokens = new TokensHelper();

    @Override
    public String getAuthorization(Input input) {
        return "Bearer " + tokens.getTokens(complaintClient).await().indefinitely().getAccessToken();
    }
}
----

Identical but for the two names. A third MCP server would need a third class.

[NOTE]
====
If `@McpClientName` does not match an MCP client name, nothing complains. The provider is simply never asked for a header, the call goes out without one, and you get a 401 that looks exactly like a misconfigured server. If you see one after this page, check the spelling here first.
====

These sit alongside `GlobexMcpHeadersSupplier` from Module 2, which is unchanged. All three are active on every orders call: the provider supplies `Authorization`, the supplier supplies `X-User-Id`.

== Add the secrets to the chart

Two files in `globex-complaint-agent-helm`, edited directly in GitLab, one commit each.

Open https://gitlab-gitlab.{openshift_subdomain}/globex/globex-complaint-agent-helm/-/edit/main/templates/secret.yaml[templates/secret.yaml^] and add the two secrets under the existing properties, reading them from values:

[source,yaml,role="copypaste"]
----
    quarkus.oidc-client.orders.credentials.secret={{ .Values.oidc.orders.secret }}
    quarkus.oidc-client.complaint.credentials.secret={{ .Values.oidc.complaint.secret }}
----

Keep the indentation. Everything under `stringData.application.properties` is indented four spaces.

Commit the change to `main`.

Then open https://gitlab-gitlab.{openshift_subdomain}/globex/globex-complaint-agent-helm/-/edit/main/values.yaml[values.yaml^] and supply them:

[source,yaml,role="copypaste",subs="attributes+"]
----
oidc:
  orders:
    secret: {keycloak_realm_internal_globex_mcp_client_secret}
  complaint:
    secret: {keycloak_realm_internal_complaints_client_secret}
----

Commit the change to `main`.

// TBC: the values keys above (.Values.oidc.orders.secret / .Values.oidc.complaint.secret)

[NOTE]
====
`values.yaml` is committed to Git, so the secret is committed with it. In production the secret would come from a secret manager, rotate on a schedule, and never reach the repository. The workshop keeps it in Git to avoid standing up another system.

Step 2 of this module removes the secret entirely.
====

[cols="1,2", options="header"]

| The code, without the secrets
