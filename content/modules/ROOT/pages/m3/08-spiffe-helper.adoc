= SPIFFE Step 2: Add the SPIFFE Helper to the Agent Pod
:numbered:
:icons: font
:source-highlighter: highlight.js

[IMPORTANT]
====
This page works in the *`globex-complaint-agent-helm`* repository, in the GitLab web editor. Three files, committed together: the helper image in `values.yaml`, a new ConfigMap, and the deployment. `deployment.yaml` reads the image from `values.yaml`, and a template that reads a value which does not exist renders as an error.
====

== The helper image

Add to `values.yaml`:

[source,yaml,role="copypaste"]
----
spiffeHelper:
  image: registry.redhat.io/zero-trust-workload-identity-manager/spiffe-helper-rhel9:v0.10.0
----

Both new containers run this image.

== The helper configuration

Create `templates/configmap.yaml`:

[source,yaml,role="copypaste"]
----
kind: ConfigMap
apiVersion: v1
metadata:
  name: spiffe-workload-agent-spiffe-helper
data:
  helper.conf: |-
    agent_address = "/spiffe-workload-agent/spire-agent.sock"
    cmd = ""
    cmd_args = ""
    cert_dir = "/svids"
    renew_signal = ""
    svid_file_name = "svid.pem"
    svid_key_file_name = "svid_key.pem"
    svid_bundle_file_name = "svid_bundle.pem"
    jwt_svids = [{jwt_audience="{{ .Values.oidcClient.orders.authServerUrl }}", jwt_svid_file_name="jwt.token"}]
    jwt_bundle_file_name  = "jwt_bundle.json"
----

`jwt_audience` is the Keycloak realm URL. SPIRE mints the SVID *for* that audience, and Keycloak rejects one minted for anything else. It reads `oidcClient.orders.authServerUrl` from the previous module page, which already ends in `/realms/internal` -- both OIDC clients point at the same realm, so either key gives the same value.

== The pod

`templates/deployment.yaml` describes a single-container pod today. It gains four things:

* An *init container*, `init-spiffe-helper`, which fetches the first SVID and exits before the agent starts.
* A *sidecar*, `spiffe-helper`, which renews it for the life of the pod. Same image and same configuration as the init container -- `-daemon-mode=false` is the only difference between them. Neither needs a `securityContext`; the pod-level one already in the file applies to all three containers.
* A `svids` *mount on the application container*, next to the `/deployments/config` mount it already has. This is the one that matters: everything else on this page exists to put a current token at `/svids/jwt.token` for the application to read.
* Three more *volumes*: `spiffe-helper-config` for the ConfigMap, `svids` as the scratch directory all three containers share, and `spiffe-workload-agent` for the socket.

That is four edits scattered through a YAML file where indentation decides whether it parses, so replace the file instead. Open `templates/deployment.yaml`, select all, and paste:

====

[NOTE]
====
`csi.spiffe.io` carries no data. It mounts the node's SPIRE agent socket into the pod. The SPIRE agent on the other end identifies the caller from the kernel, by process, and cross-checks it with the kubelet, so the pod supplies no credential and cannot misreport which pod it is.

The SPIFFE ID it is issued is built from the pod's namespace and service account, and the Keycloak client is pinned to that exact string. Leave `serviceAccountName` alone.
====

== Commit

Commit `values.yaml`, `templates/configmap.yaml` and `templates/deployment.yaml` to `main`.

The pod will roll out with three containers and a token on disk, but the application is not reading it yet -- it still authenticates with the client secret. That is SPIFFE Step 3.
