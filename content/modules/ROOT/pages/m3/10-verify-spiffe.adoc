= SPIFFE Step 4: Confirm the Agent Has No Secret
:numbered:
:icons: font
:source-highlighter: highlight.js

== Watch the rollout

Open the https://openshift-gitops-server-openshift-gitops.{openshift_subdomain}/[ArgoCD console^] and open `globex-complaint-agent`.

The pod now has three containers, and the order they come up in is the thing to watch: `init-spiffe-helper` must complete before anything else starts. If it hangs, the CSI volume is not mounting and no SVID is being issued -- the agent container never starts at all.

Open the pod and select the `init-spiffe-helper` container on the *LOGS* tab:

image::m3/spiffe-helper-init-log.png[link=self,window=_blank]

It fetched a JWT-SVID to `/svids/jwt.token` and exited, which is what lets the agent container start.

The pod should report *2/2* containers running, `globex-complaint-agent` and `spiffe-helper`, with `init-spiffe-helper` completed.

[WARNING]
====
If it reports *1/1* with no `spiffe-helper` container, only the init container landed. The agent will work for about five minutes and then start failing on every reconnect with:

....
mcp server reconnection failed: io.quarkus.oidc.client.OidcClientException:
{"error":"invalid_client","error_description":"Token is not active"}
....

That is Keycloak rejecting an expired SVID. The init container wrote one token and exited; without the sidecar nothing renews it. Go back to SPIFFE Step 2 and re-paste the whole of `templates/deployment.yaml` -- a partial edit that drops the sidecar, or leaves two `containers:` keys, produces exactly this.
====

== Test it

Nothing about the behaviour should change. Open the https://globex-web-globex.{openshift_subdomain}/[Globex storefront^], sign in as `asilva` / `openshift`, go to *Customer Care*, and raise a complaint exactly as you did before.

It still works, and the agent authenticated to Keycloak twice with no secret anywhere in the chart, the repository, or the image.

== See the identity the platform issued

Open the pod again and select the `spiffe-helper` container -- the sidecar this time, not the init container -- on the *LOGS* tab:

....
level=info msg="Using configuration file: \"/etc/helper.conf\"" system=spiffe-helper
level=info msg="Launching daemon" system=spiffe-helper
level=info msg="Watching for X509 Context" system=spiffe-helper
level=info msg="Watching for JWT Bundles" system=spiffe-helper
level=info msg="Received update" spiffe_id="spiffe://globex.com/ns/globex-complaint-agent/sa/globex-complaint-agent" system=spiffe-helper
level=info msg="JWT SVID updated" system=spiffe-helper
level=info msg="JWT bundle updated" system=spiffe-helper
level=info msg="X.509 certificates updated" system=spiffe-helper
....

`spiffe_id` on the *Received update* line is the identity SPIRE attested this pod as, and nobody typed it anywhere. It is assembled from the pod's namespace and service account by a cluster-wide template the operator installs, which is why it reads `/ns/globex-complaint-agent/sa/globex-complaint-agent`. Change the service account and the identity changes with it.

`Launching daemon` is the difference from the init container's log above. This one stays running.

Leave the tab open for a few minutes. `JWT SVID updated` appears again, roughly every two and a half minutes -- `spiffe-helper` renews at half the remaining lifetime, so a five-minute SVID is replaced on a 2m31s cycle, indefinitely, with nothing scheduled and nobody rotating anything.

== Optional: look at the files

The credential is a file, not a Kubernetes Secret. In the https://console-openshift-console.{openshift_subdomain}/k8s/ns/globex-complaint-agent/pods[OpenShift console^], open the running pod, go to the *Terminal* tab, and select the `globex-complaint-agent` container:

[source,sh,role="copypaste"]
----
ls -l /svids
----

Five files, written by the helper:

[cols="1,2", options="header"]
|===
| File | What it is

| `jwt.token`
| The JWT-SVID. This is the one that authenticates to Keycloak.

| `svid.pem`, `svid_key.pem`
| An X.509-SVID and its key. `spiffe-helper` always writes these; nothing here uses them.

| `svid_bundle.pem`, `jwt_bundle.json`
| The trust bundles for the domain.
|===

Decode the JWT payload:

[source,sh,role="copypaste"]
----
cut -d. -f2 /svids/jwt.token | base64 -d 2>/dev/null; echo
----

[source,json]
----
{
  "aud": [ "https://sso.<your subdomain>/realms/internal" ],
  "exp": 1791234567,
  "iat": 1791234267,
  "iss": "https://oidc-discovery.<your subdomain>",
  "sub": "spiffe://globex.com/ns/globex-complaint-agent/sa/globex-complaint-agent"
}
----

Three of those are worth stopping on:

* `exp - iat` is *300* -- five minutes, as set on the `SpireServer` resource.
* `aud` is the realm URL you typed into `helper.conf`. SPIRE minted the token for that audience and Keycloak rejects one minted for anything else.
* `sub` is the SPIFFE ID, and nobody typed it anywhere. The ZTWIM operator assembled it from the pod's namespace and service account.

[NOTE]
====
This file is a live credential. For the next few minutes anyone holding it can authenticate to Keycloak as the agent. That it stops mattering so quickly is the point of the exercise -- compare it with the client secret from the previous page, which was valid until someone went and changed it.

Do not paste it into an online JWT decoder. The command above does the same job without sending the token anywhere.
====

== Confirm the secret is gone

Two views, one on each side.

*The chart.* In the console, go to *Workloads* -> *Secrets* in the `globex-complaint-agent` project, open the `globex-complaint-agent` secret, and reveal `application.properties`. On the previous page this showed `quarkus.oidc-client.orders.credentials.secret=` with the secret in clear. The `quarkus.oidc-client.*` lines are still there and there is no `credentials.secret` among them.

*Keycloak.* Open the https://sso.{openshift_subdomain}/admin[admin console^] as `admin` / `{common_password}`, switch to the `internal` realm, and open *Clients* -> `globex-agent-spiffe` -> *Credentials*. The *Client Authenticator* is *Signed JWT - Federated*, with *Identity provider* `spiffe` and *Federated subject* set to the SPIFFE ID you just decoded. There is no client secret field and no regenerate button. Compare with `globex-mcp-client` in the same realm, which still has both.

== Optional: do the grant by hand

This removes the application from the picture entirely. Copy the token out of the pod, then from a terminal:

[source,sh,subs="attributes+"]
----
curl -s https://sso.{openshift_subdomain}/realms/internal/protocol/openid-connect/token \
  -d grant_type=client_credentials \
  -d client_id=globex-agent-spiffe \
  -d client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-spiffe \
  --data-urlencode client_assertion="<the contents of /svids/jwt.token>"
----

An access token comes back and no secret was involved anywhere in the exchange.

Run it again six minutes later with the same assertion and Keycloak answers `{"error":"invalid_client","error_description":"Token is not active"}` -- the five-minute lifetime, demonstrated rather than asserted. It is also the error you would see in the agent log if the renewing sidecar were missing.

== What changed

[cols="1,1,1", options="header"]
|===
| | Before SPIFFE | Now

| What the agent presents
| A client secret
| A JWT-SVID, signed by SPIRE

| Where it comes from
| `values.yaml`, via a Kubernetes Secret
| The SPIRE agent, over a Unix socket

| How long it lasts
| Until someone rotates it
| Five minutes

| What Keycloak checks
| That the string matches
| That the platform attested the workload

| What is in Git
| The secret
| A SPIFFE ID, which is a name, not a credential
|===

The MCP servers were not touched. From their side nothing happened -- the same Keycloak, the same access token, the same audience check. Only how the agent proved itself to Keycloak changed.
