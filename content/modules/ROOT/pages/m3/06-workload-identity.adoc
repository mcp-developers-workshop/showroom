== Why the client secret is not enough

Enabling OIDC authentication across the agent and the MCP servers left the agent holding a Keycloak identity of its own, and both servers accepting it. That identity is a client ID and a client secret.

Keycloak checks that the secret matches the one it holds for that client -- nothing more. It cannot tell whether the caller is your agent or a laptop that copied the secret out of the Git repository you put it in on the last page.

That is the weakness of any shared secret: it proves *what you have*, not *who you are*. And because changing it means changing it everywhere at once, it is rarely changed at all.

== What SPIFFE is

SPIFFE is a standard for giving a workload an identity based on what it actually is and where it actually runs, instead of a secret it carries.

Three terms cover it:

[cols="1,3", options="header"]
|===
| Term | What it means

| Trust domain
| The boundary that issues identities -- in practice, your cluster.

| SPIFFE ID
| The name of one workload, written as a URI: `spiffe://globex.com/ns/globex-complaint-agent/sa/globex-complaint-agent`. A username for a pod rather than a person.

| SVID
| The credential that proves the SPIFFE ID, as an X.509 certificate or a JWT. It is valid for minutes, not forever.
|===

The agent stores none of this. It asks for an SVID when it needs one and gets a fresh one each time.

== What it takes to run it

The identity has to be issued by something that can verify the claim independently of the workload, which means the platform it runs on. SPIRE is the implementation:

* A *SPIRE server* -- the certificate authority for the trust domain.
* A *SPIRE agent* on every node. When a pod asks for an identity, the agent asks the kubelet what that pod really is -- its namespace, its service account, its image -- and only then issues the SVID. That check is called *attestation*.
* A *registration entry* per workload, mapping those pod properties to a SPIFFE ID. This is the one piece a human writes.
* A consumer that trusts the trust domain. Here that is Keycloak, which has to accept an SVID where it currently expects a client secret.

The workload talks to its node's SPIRE agent over a local Unix socket, so there is no credential to put in a chart, in Git, or in an environment variable, and nothing to rotate on a schedule.

== What you build over the next four pages

A SPIRE agent attests the agent pod and issues it a short-lived JWT-SVID. The agent sends that SVID to Keycloak in place of the client secret, as a *client assertion*. Keycloak matches it to the Keycloak client the agent already uses and issues the same access token as before -- so the MCP servers need no change, and both `quarkus.oidc-client.*` blocks from the last page stay. What goes away is the secret in `values.yaml`.

== What is already on the cluster

The platform half is installed for you. The *Zero Trust Workload Identity Manager* operator runs SPIRE on OpenShift through four custom resources:

[cols="1,2", options="header"]
|===
| Resource | What it does

| `ZeroTrustWorkloadIdentityManager`
| Sets the trust domain (`globex.com`) and cluster name for everything below.

| `SpireServer`
| The CA for the trust domain. JWT-SVIDs it issues are valid for *five minutes*.

| `SpireAgent`
| One per node. Attests pods using the Kubernetes projected service account token, then answers Workload API requests.

| `SpiffeCSIDriver`
| Publishes the SPIRE agent's Unix socket into a pod as a volume, so the workload can reach the Workload API without a host mount.
|===

Keycloak is configured for it too -- the `client-auth-federated` and `spiffe` features are enabled on the server, and the `internal` realm carries:

* An identity provider named `spiffe`, of type `CLIENT_ASSERTION`, pointing at the trust domain `spiffe://globex.com` and SPIRE's bundle endpoint. This is what lets Keycloak verify an SVID it is handed.
* A client whose `clientAuthenticatorType` is `federated-jwt` rather than `client-secret`, with the agent's SPIFFE ID recorded on it as `jwt.credential.sub`.

So Keycloak will not look up a secret for this client at all. It verifies the SVID's signature against the trust domain, reads the subject, and checks it matches the SPIFFE ID on the client.

[NOTE]
====
Optional. To see the identity provider, open the https://sso.{openshift_subdomain}/admin[Keycloak admin console^] as `admin` / `{common_password}`, switch to the `internal` realm, and go to *Identity providers* -> *spiffe*.

The bundle endpoint is where Keycloak fetches SPIRE's public keys to check the signature -- it is SPIRE's OIDC discovery route, not a Keycloak address. Both are already set; nothing here needs changing.

== How the agent gets its SVID

The agent does not call the Workload API itself. A helper does it, and leaves the token on disk where Quarkus can read it:

....
SPIRE agent (node)
   |  Unix socket, mounted by the CSI driver
   v
spiffe-helper (init container)   -- fetches the first SVID before the agent starts
spiffe-helper (sidecar)          -- renews it, every few minutes, for the life of the pod
   |
   v
/svids/jwt.token   <-- shared emptyDir, read by the agent container
....

The init container matters: a JWT-SVID lasts five minutes, so the agent must not start before one exists, and must never be left holding an expired one.
