= Authenticate the Agent to the MCP Servers
:numbered:
:icons: font
:source-highlighter: highlight.js

[IMPORTANT]
====
This page switches projects. Everything here happens in the *`globex-complaint-agent`* folder -- the agent, not either MCP server. Open a terminal there before continuing.
====

The agent already holds a token -- the user's JWT from the chatbot. It cannot use that one to call an MCP server.

It would not work: the JWT is issued by the `globex` realm for a different audience, so `globex-mcp-server` rejects it. And it is specifically forbidden. The MCP specification rules out passing a client's token straight through to a downstream server, because forwarding a token means some other service can replay it, and the audience check you set on page 2 stops meaning anything.

So the agent gets a second token of its own, and the two travel together:

....
chatbot  --user JWT (globex realm)-->  agent  --agent token (internal realm)-->  MCP server
                                              --X-User-Id: asilva-------------->
....

[cols="1,1,1", options="header"]
|===
| | User JWT | Agent token

| Realm
| `globex`
| `internal`

| Who it describes
| The signed-in customer
| The agent workload

| Who issues it to whom
| Keycloak, to the chatbot, after the customer signs in
| Keycloak, to the agent, on a client ID and secret

| Where it stops
| The agent validates it and does not pass it on
| The MCP servers validate it
|===

`X-User-Id` is unchanged from Module 2. The agent validates the user's JWT, takes `preferred_username` from it -- `AuthoritativeUserIdHolder` -- and sends that value. What is new is the token beside it.

== Add the OIDC client extension

[source,sh,role="copypaste"]
----
mvn quarkus:add-extension -Dextensions="oidc-client"
----

`quarkus-oidc` is already on the agent, validating the user's JWT from the chatbot. That is the resource server side. What is new here is the client side: getting a token of the agent's own.

[WARNING]
====
`quarkus.oidc.*` and `quarkus.oidc-client.*` are different configuration trees and they are one character apart.

* `quarkus.oidc.*` -- already configured, do not touch it. The agent *validating* incoming user tokens against the `globex` realm.
* `quarkus.oidc-client.*` -- what you add below. The agent *fetching* its own token from the `internal` realm.

Two realms, two opposite directions.
====

The agent has a separate Keycloak identity for each MCP server, named `orders` and `complaint` after the MCP clients from Module 2. Each is a *client credentials* grant: the agent presents a client ID and secret to Keycloak and gets back an access token that says it is that client. No user is involved.

[NOTE]
====
`globex-mcp-client` and `globex-agent-complaints-client` already exist in the `internal` realm, with client credentials enabled and their secrets generated, created when your lab environment is provisioned. You are wiring the agent up to them, not creating them.
====

Nothing goes in `application.properties` on this page. The realm URL differs per cluster and the secrets must not be in the image, so all six properties come from the chart. Write the code first and push it, then supply the configuration while the build runs.

== Write the auth providers

An MCP client asks an `McpClientAuthProvider` for the `Authorization` header on every call. `@McpClientName` ties one provider to one MCP client, so two MCP clients need two providers -- there is no way to write a single class that covers both.

These go in the same `auth` package as `GlobexMcpHeadersSupplier` from Module 2:

[source,sh,role="copypaste"]
----
mkdir -p src/main/java/org/globex/retail/ai/complaint/auth
touch src/main/java/org/globex/retail/ai/complaint/auth/GlobexMcpAuthProvider.java
touch src/main/java/org/globex/retail/ai/complaint/auth/GlobexComplaintMcpAuthProvider.java
----

[IMPORTANT]
====
Check two things before you paste, or the editor will fill both files with errors:

* *You are in `globex-complaint-agent`.* `McpClientName` and `McpClientAuthProvider` come from `quarkus-langchain4j-mcp`, which is the MCP *client* library. Neither MCP server has that dependency, so in those projects these types do not exist at all.
* *The extension is added and the project has reloaded.* Create the classes before `quarkus-oidc-client` is on the classpath and the editor reports every import as unresolved -- including the ones that were already available -- because the file as a whole fails to resolve.
====

Open `GlobexMcpAuthProvider.java` and paste:

[source,java,role="copypaste"]
----
package org.globex.retail.ai.complaint.auth;

import io.quarkiverse.langchain4j.mcp.auth.McpClientAuthProvider;
import io.quarkiverse.langchain4j.mcp.runtime.McpClientName;
import io.quarkus.oidc.client.NamedOidcClient;
import io.quarkus.oidc.client.OidcClient;
import io.quarkus.oidc.client.runtime.TokensHelper;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
@McpClientName("orders")
public class GlobexMcpAuthProvider implements McpClientAuthProvider {

    @Inject
    @NamedOidcClient("orders")
    OidcClient globexStoreClient;

    TokensHelper tokens = new TokensHelper();

    @Override
    public String getAuthorization(Input input) {
        return "Bearer " + tokens.getTokens(globexStoreClient).await().indefinitely().getAccessToken();
    }
}
----

Two annotations carry the name `orders`, and they refer to different things:

* `@McpClientName("orders")` is the *MCP client* -- the one configured by `quarkus.langchain4j.mcp.orders.*` and named in `@McpToolBox("orders")`. It tells Quarkus which client this provider supplies the header for.
* `@NamedOidcClient("orders")` is the *OIDC client* -- `quarkus.oidc-client.orders.*`, which you add to the chart below. It is where the token comes from.

Both names must match their configuration exactly. A mismatch binds nothing.

`TokensHelper` caches the token and refreshes it when it expires, so Keycloak is not called on every tool invocation.

Now `GlobexComplaintMcpAuthProvider.java`:

[source,java,role="copypaste"]
----
package org.globex.retail.ai.complaint.auth;

import io.quarkiverse.langchain4j.mcp.auth.McpClientAuthProvider;
import io.quarkiverse.langchain4j.mcp.runtime.McpClientName;
import io.quarkus.oidc.client.NamedOidcClient;
import io.quarkus.oidc.client.OidcClient;
import io.quarkus.oidc.client.runtime.TokensHelper;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
@McpClientName("complaint")
public class GlobexComplaintMcpAuthProvider implements McpClientAuthProvider {

    @Inject
    @NamedOidcClient("complaint")
    OidcClient complaintClient;

    TokensHelper tokens = new TokensHelper();

    @Override
    public String getAuthorization(Input input) {
        return "Bearer " + tokens.getTokens(complaintClient).await().indefinitely().getAccessToken();
    }
}
----

Identical but for the two names. A third MCP server would need a third class.

[NOTE]
====
If `@McpClientName` does not match an MCP client name, nothing complains. The provider is simply never asked for a header, the call goes out without one, and you get a 401 that looks exactly like a misconfigured server. If you see one after this page, check the spelling here first.
====

These sit alongside `GlobexMcpHeadersSupplier` from Module 2, which is unchanged. All three are active on every orders call: the provider supplies `Authorization`, the supplier supplies `X-User-Id`.

== Configure the OIDC clients in the chart

Two files in `globex-complaint-agent-helm`, edited directly in GitLab, one commit each. Do them in this order: a template that reads a value which does not exist yet fails to render, and ArgoCD reports the whole application as broken until the second commit lands.

Open https://gitlab-gitlab.{openshift_subdomain}/globex/globex-complaint-agent-helm/-/edit/main/values.yaml[values.yaml^] and add a new block at the end of the file:

[source,yaml,role="copypaste",subs="attributes+"]
----
oidcClient:
  orders:
    authServerUrl: https://sso.{openshift_subdomain}/realms/internal
    clientId: globex-mcp-client
    secret: {keycloak_realm_internal_globex_mcp_client_secret}
  complaint:
    authServerUrl: https://sso.{openshift_subdomain}/realms/internal
    clientId: globex-agent-complaints-client
    secret: {keycloak_realm_internal_complaints_client_secret}
----

[WARNING]
====
`oidcClient` is a new top-level key. There is already an `oidc` key in this file for the agent as a resource server -- leave it alone, and do not merge these entries into it. Two keys with the same name in one YAML file do not merge; the second silently replaces the first, and you would lose the agent's existing OIDC configuration.
====

Commit the change to `main`.

Then open https://gitlab-gitlab.{openshift_subdomain}/globex/globex-complaint-agent-helm/-/edit/main/templates/secret.yaml[templates/secret.yaml^] and add six properties under the existing ones, all reading from the values you just added:

[source,yaml,role="copypaste"]
----
    quarkus.oidc-client.orders.auth-server-url={{ .Values.oidcClient.orders.authServerUrl }}
    quarkus.oidc-client.orders.client-id={{ .Values.oidcClient.orders.clientId }}
    quarkus.oidc-client.orders.credentials.secret={{ .Values.oidcClient.orders.secret }}
    quarkus.oidc-client.complaint.auth-server-url={{ .Values.oidcClient.complaint.authServerUrl }}
    quarkus.oidc-client.complaint.client-id={{ .Values.oidcClient.complaint.clientId }}
    quarkus.oidc-client.complaint.credentials.secret={{ .Values.oidcClient.complaint.secret }}
----

Keep the indentation. Everything under `stringData.application.properties` is indented four spaces.

The `quarkus.oidc.*` block already in this file is the agent as a resource server, against the `globex` realm. These six are the other direction.

Commit the change to `main`.

[NOTE]
====
If ArgoCD shows `nil pointer evaluating interface {}.secret`, the template is reading a key that `values.yaml` does not define. The two files disagree -- check that the path after `.Values.` matches the block above exactly, including `oidcClient` rather than `oidc`.
====
