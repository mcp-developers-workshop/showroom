= Send the User ID with the Tool Call
:numbered:
:icons: font
:source-highlighter: highlight.js

The MCP server reads `X-User-Id` off the request, and the agent's MCP client is not sending it. The value has to be the user who signed in, so it changes on every request -- it cannot be a fixed header in the configuration.

The signed-in user is already known: `AgentResource` reads `preferred_username` from the token. What is missing is a way to carry that value from the incoming HTTP request to the outgoing MCP call, which happens later, inside the agent, on a different thread.

Three pieces: a request-scoped bean to hold the value, the resource to put it there, and a headers supplier the MCP client asks for headers on every call.

== Hold the user ID for the request

Open a new terminal in IBM Bob -- the agent and the chatbot are running in theirs. From the `globex-complaint-agent` folder:

[source,sh,role="copypaste"]
----
mkdir -p src/main/java/org/globex/retail/ai/complaint/service
touch src/main/java/org/globex/retail/ai/complaint/service/AuthoritativeUserIdHolder.java
----

Open the new file in Bob and paste:

[source,java,role="copypaste"]
----
package org.globex.retail.ai.complaint.service;

import jakarta.enterprise.context.RequestScoped;

@RequestScoped
public class AuthoritativeUserIdHolder {

    private String userId;

    public AuthoritativeUserIdHolder() {}

    public String getUserId() {
        return userId;
    }

    public void setUserId(String userId) {
        this.userId = userId;
    }
}
----

[NOTE]
====
If Bob flags the new file with errors that do not look real -- an unresolved package, unknown imports -- the Java language server has not picked up a file created from the terminal. Open the command palette and run *Java: Restart Java Language Server*.
====

`@RequestScoped` means one instance per HTTP request, so two customers using the agent at the same time cannot see each other's value.

The value it holds comes from the verified token, not from the conversation, so the model cannot influence it. Hence *authoritative* in the class name.

== Set it from the token

`AgentResource` already reads the username out of the token. It takes three edits to hand that value to the holder.

Open `src/main/java/org/globex/retail/ai/complaint/rest/AgentResource.java`.

Add the import, below the existing `ComplaintService` import:

[source,java,role="copypaste"]
----
import org.globex.retail.ai.complaint.service.AuthoritativeUserIdHolder;
----

Inject the holder, below the existing `complaintService` field:

[source,java,role="copypaste"]
----
    @Inject
    AuthoritativeUserIdHolder authoritativeUserIdHolder;
----

Then, inside the `handleUserRequest` method, add this line to the `.onItem().transform(r -> {` block:

[source,java,role="copypaste"]
----
                    authoritativeUserIdHolder.setUserId(userName);
----

It goes directly above:

[source,java]
----
                    JsonObject jsonObject = new JsonObject(r);
----

== Supply the header on every MCP call

The MCP client asks for headers each time it calls a tool. Implement `McpHeadersSupplier` and return `X-User-Id` from the holder.

In the same terminal:

[source,sh,role="copypaste"]
----
mkdir -p src/main/java/org/globex/retail/ai/complaint/auth
touch src/main/java/org/globex/retail/ai/complaint/auth/GlobexMcpHeadersSupplier.java
----

Open the new file in Bob and paste:

[source,java,role="copypaste"]
----
package org.globex.retail.ai.complaint.auth;

import dev.langchain4j.mcp.client.McpCallContext;
import dev.langchain4j.mcp.client.McpHeadersSupplier;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.context.control.ActivateRequestContext;
import jakarta.inject.Inject;
import org.globex.retail.ai.complaint.service.AuthoritativeUserIdHolder;

import java.util.Map;

@ApplicationScoped
public class GlobexMcpHeadersSupplier implements McpHeadersSupplier {

    @Inject
    AuthoritativeUserIdHolder authoritativeUserIdHolder;

    @Override
    @ActivateRequestContext
    public Map<String, String> apply(McpCallContext mcpCallContext) {
        String userId;
        if (authoritativeUserIdHolder.getUserId() == null) {
            userId = "system";
        } else {
            userId = authoritativeUserIdHolder.getUserId();
        }
        return Map.of("X-User-Id", userId);
    }
}
----

Every tool call the client makes now carries the header, and the value is whoever is signed in.

[NOTE]
====
`@ActivateRequestContext` is there because the tool call does not run on the thread that received the HTTP request. The fallback to `system` covers a call made with no request context at all -- that value is not a customer, so the MCP server returns nothing for it.
====

== File the complaint

Pick a product from one of the orders and describe the problem:

[source,text,role="copypaste"]
----
I want to raise a complaints about the Stojo Collapsible Silicone Bottle. the cap was broken on arrival. It is such a critical problem for me. I want a replacement
----

The agent works through the rest of the prompt's conversation flow. It reads the issue type as `Defect`, the severity as `Critical` and the resolution as `Replacement`, ties them to order 231, and asks you to confirm:

image::m2/chatbot-complaint-summary.png[link=self,window=_blank]

Reply `yes`.

image::m2/chatbot-no-complaint-id.png[link=self,window=_blank]

The agent repeats the details back and then says it cannot generate a complaint ID. It has nothing to file the complaint with. `getOrdersByCustomerId` is the only tool it has, and reading orders is not raising a complaint.
