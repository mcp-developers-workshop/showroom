= Summary

You took an agent that could only talk about complaints and gave it the tools to act on them:

* Connected the agent to the model, with the API key in `.env` so it stays out of your commits.
* Added an MCP client for the orders server you built in Module 1, and rewrote the prompt so the agent fetches the customer's orders instead of asking for an order ID.
* Drove the agent from the chatbot and watched the first tool call fail in the MCP server's log, for want of the `X-User-Id` header.
* Carried the signed-in user from the verified token to every MCP call, through a request-scoped holder and an `McpHeadersSupplier`.
* Added a second MCP client for the complaints server, listed both in `@McpToolBox`, and filed a complaint against a real order.
* Pushed the code, set the model and the two MCP URLs in the Helm chart, and let ArgoCD build and roll out the agent.

Adding the second server took one property and one word in an annotation. The agent's code does not grow as its capabilities do, because a tool is discovered at startup rather than written against.

The user ID now comes from the token, never from the conversation, so the model cannot claim to be another customer. The MCP server still trusts whatever header it is sent, and anything that can reach the route can set that header. Module 3 closes that gap.
